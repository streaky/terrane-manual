# 8. Namespaces, Imports, and Packages

The strict reporting tool now has several distinct responsibilities: an application chooses input and recovery policy, reporting code validates and presents a batch, and an error type describes invalid entries. Keeping all of that in one file makes the complete flow visible, but it also makes every declaration appear equally close to every other declaration.

A project needs a larger form of the boundaries we already created with functions. Terrane uses namespaces to give declarations stable identities, imports to bring selected names into a scope, and a package manifest to tell the compiler which source tree belongs to the build.

Splitting files should not alter the program's behavior. This chapter will move Chapter 7's reporting tool into three namespaces and run it through the same compiler pipeline.

## From one file to a project

The single source currently contains three conceptual regions:

```text
invalid-report-entry
require-entry, strict-total, progress-label, print-report
main
```

Those regions have different reasons to change:

- error contracts change when the domain distinguishes failures differently;
- reporting changes when validation, calculation, or presentation changes;
- the application changes when inputs and recovery policy change.

That gives us a useful project shape:

```text
work-report/
├── package.toml
├── app/
│   └── main.trn
├── errors/
│   └── invalid-report-entry.trn
└── reporting/
    └── report.trn
```

Files are not the program's semantic identity. The declarations inside them belong to namespaces. The manifest maps namespace roots to directory roots so source discovery is bounded and reproducible.

A split is worthwhile when it reveals a boundary, not merely when a file reaches an arbitrary length. Three files named `part-one.trn`, `part-two.trn`, and `part-three.trn` would reduce line counts without explaining the program. `app`, `errors`, and `reporting` tell a reader why each part exists.

## Namespaces and paths

Every Terrane source unit begins by declaring its namespace:

```terrane
namespace work-report/reporting
```

Namespace segments use lowercase ASCII letters, digits, and internal hyphens. `/` separates every namespace boundary:

```text
work-report
work-report/reporting
work-report/reporting/renderers
```

A leading slash anchors a lookup at the namespace root:

```terrane
from /work-report/errors import invalid-report-entry
```

The slash is a namespace separator, not a host filesystem root and not an identifier character. `/work-report/errors` means the root namespace path `work-report/errors`; it does not mean `/work-report/errors` on Linux.

Relative namespace paths are also available. From `work-report/reporting`, this names the sibling namespace `work-report/errors`:

```terrane
from ../errors import invalid-report-entry
```

Absolute paths are useful when an example should be readable without first calculating its current location. Relative paths can make a tightly related subtree easier to move. Choose deliberately and remain consistent within a local part of the project.

Namespace identity is exact. The compiler does not silently lowercase `Work-Report`, reinterpret dots as separators, or scan the entire filesystem for something with a similar name. A misspelling should produce a source diagnostic rather than a surprising nearby import.

## Imports

An import binds an object from another namespace into the scope containing the import. The reporting source needs the map constructor and the domain error:

```terrane
from /core/collections import map
from /work-report/errors import invalid-report-entry
```

These are selective imports. Only the named objects enter the scope.

An alias changes the local spelling without changing the imported object's identity:

```terrane
from /work-report/reporting import print-report as show-report
```

The application can now write:

```terrane
show-report; 'Corrected report', 18, corrected
```

The function remains `/work-report/reporting::print-report`. `show-report` is the name by which this scope refers to it; the alias does not create a wrapper or a second function.

A namespace-wide import binds every public function-body object exported by that namespace:

```terrane
import /work-report/reporting
```

Selective imports are usually clearer when a module needs only one or two objects. Namespace-wide imports are useful when the imported namespace deliberately presents a small, coherent vocabulary. They should not be used to avoid learning where a name comes from.

Imports are structural compile-time declarations. They are not ordinary function calls and do not perform runtime initialization merely because the source mentions them. The compiler resolves them before ordinary expression evaluation.

The default prelude still applies. `print`, task-scope constructs, UTF descriptors, and the ordinary scalar type constructs listed earlier do not need imports. Operational facilities such as collections remain explicit:

```terrane
from /core/collections import map

function main;
  values map of string, int = map
  print; values.length
```

Importing `print` in an ordinary prelude-enabled project is redundant. Importing `map` communicates a real dependency on the collection facility.

## Organizing the source tree

Our manifest will map three namespace roots directly to three directories:

```toml
[namespaces]
"work-report/app" = "app"
"work-report/errors" = "errors"
"work-report/reporting" = "reporting"
```

A file immediately inside `reporting/` therefore declares:

```terrane
namespace work-report/reporting
```

If that directory contained `format/text.trn`, its namespace would be `work-report/reporting/format`. The namespace tree and directory tree continue together beneath the mapped root.

The compiler checks that declared namespaces agree with their mapped locations. Moving `report.trn` into `errors/` without changing its namespace is not a harmless organizational choice: the file would claim one identity while occupying the source root assigned to another. Terrane rejects that disagreement.

The manifest discovers `.trn` files recursively beneath declared roots. A source file outside every mapping is not quietly added because it happens to be nearby. Conversely, compilation is not driven by following imports until no more files happen to appear. The declared roots bound the source set, and the compiler assembles that complete set deterministically.

This matters for reproducibility. Two machines should not build different programs because one has an extra scratch file in an unrelated directory or because filesystem iteration returns a different order.

Organize by stable responsibility rather than by compiler phase. The application should not need folders named `parser-input`, `typed`, or `generated-rust`; those are compiler concerns. Our project folders name concepts in the reporting application.

## Visibility

Declarations are public by default. A public object may be imported from another namespace:

```terrane
function print-report; title string, target int, entries map of string, int
  # ...
```

Not every implementation detail should become part of that boundary. The reporting namespace has two helpers:

```terrane
private function require-entry throws invalid-report-entry; entry-name string, units int
  # ...

private function strict-total int throws invalid-report-entry; entries map of string, int
  # ...
```

`print-report` may call them because all three belong to the same namespace. The application may import `print-report`, but an attempt to import `strict-total` is rejected.

Visibility answers who may name a declaration; it is not a request for runtime secrecy. Marking a function `private` does not encrypt its behavior or hide generated machine code. It keeps the source-level contract honest by preventing other namespaces from depending on an implementation detail.

Use `public` explicitly when a strict visibility policy or API-focused source benefits from the emphasis. Under the ordinary default, omitting `public` still exports the declaration. `private` is therefore the important marker in our small package.

`protected` supports deliberate inheritance and parent-to-child composition boundaries. It becomes relevant when a subclass needs a member unavailable to unrelated callers. Do not use it as a vague middle setting between public and private; choose it only when the inheritance relationship is part of the contract.

A useful package surface is usually smaller than its implementation. Every public name can become something another source file expects to remain stable. Begin with the operations callers need, not every helper that happens to exist today.

## The package manifest

At the project root, create `package.toml`:

```toml
package = "work-report.tutorial"
prelude = true

[namespaces]
"work-report/app" = "app"
"work-report/errors" = "errors"
"work-report/reporting" = "reporting"
```

`package` gives the build graph a non-empty package identity. It is not a namespace declaration and does not force source namespaces to repeat its punctuation.

`prelude = true` enables the ordinary default prelude. It is optional because `true` is the default, but retaining it in a tutorial manifest makes the choice visible. A specialized environment may disable it and import every required object explicitly.

`[namespaces]` is required and non-empty. Each key is a canonical namespace root; each value is a distinct relative directory root. Absolute paths and parent traversal are rejected because a package should not acquire undeclared source by reaching outside its root.

The manifest is authored TOML, not Terrane source. Unknown fields are errors rather than ignored guesses. This strictness catches misspelled build settings before they become machine-dependent behavior.

A direct `.trn` command from earlier chapters still works because the compiler creates an implicit single-file package around it. Moving to `package.toml` makes the source set, namespace mapping, profile, and dependencies explicit without introducing a second compiler path.

## Dependencies

A package may depend on Terrane packages, projected Rust crates, and system libraries. Dependency declaration and name import are separate questions:

- the manifest and lock data determine which package or crate version exists in the build;
- source imports bind particular exported objects into a scope;
- a source `use` declaration records a build dependency where that dependency form applies; it does not itself bind every supplied API name.

Our project uses compiler-bundled core facilities, so it needs no third-party dependency entry. It imports `map` and `throwable` through their `/core` namespaces.

Rust dependencies are declared in `package.toml`, never smuggled into source through an undeclared path. A later package might contain:

```toml
[rust-dependencies]
some-crate = { version = "=1.2.3", default-features = false, features = ["useful-feature"] }
```

Its projected source objects then live beneath a reserved `/deps` namespace. The resolved lock, features, target, and toolchain are part of the actual interface. Chapter 16 will cross that boundary directly; for now, the important point is that dependencies remain inspectable build inputs.

Capabilities are likewise explicit. Filesystem, networking, process, entropy, threading, and TLS facilities may require permission from the selected package profile. Importing a gated facility without the required capability is a diagnostic, not a request for the compiler to weaken policy silently.

A reproducible lock graph prevents “the same” package from changing beneath the source. Generated Cargo files remain compiler output; the Terrane package manifest is the authored contract.

## Building and running a package

From the directory containing `package.toml`, check the complete package:

```console
terrane check .
```

The manifest path is also accepted explicitly:

```console
terrane check package.toml
```

Both forms load the mapped source set and run the shared compiler pipeline. `check` does not mean “parse only”; it carries the package through generated-Rust validation so a source program is not declared healthy while its lowering fails.

Inspect generated Rust with:

```console
terrane rust package.toml
```

Build an executable with:

```console
terrane build package.toml
```

For an optimized executable:

```console
terrane build --release package.toml
```

Run the package directly:

```console
terrane run package.toml
```

`check`, `rust`, `build`, and `run` use one source, resolution, semantic, and lowering pipeline. The command chooses how far to take the same compilation result; it does not select a different interpretation of the language.

The package's entry point is still the real `main` function. Splitting the project does not replace language-level entry with a manifest script.

## Project: split the reporting tool across files

Create the directory tree shown at the start of the chapter.

### `package.toml`

```toml
package = "work-report.tutorial"
prelude = true

[namespaces]
"work-report/app" = "app"
"work-report/errors" = "errors"
"work-report/reporting" = "reporting"
```

### `errors/invalid-report-entry.trn`

```terrane
namespace work-report/errors

from /core/errors import throwable

class invalid-report-entry implements throwable
  message string = ''
  entry-name string = ''
  units int = 0

  function construct; entry-name string, units int
    if entry-name == ''
      this.message = 'entry name must not be empty'
    else
      this.message = 'work units must be greater than zero'
    this.entry-name = entry-name
    this.units = units

  function render string;
    return 'invalid report entry: '.concat; this.message
```

The namespace exports the error class. It imports only the `throwable` contract needed to define that class.

### `reporting/report.trn`

```terrane
namespace work-report/reporting

from /core/collections import map
from /work-report/errors import invalid-report-entry

private function require-entry throws invalid-report-entry; entry-name string, units int
  if entry-name == '' or units <= 0
    throw instance invalid-report-entry; entry-name, units

private function strict-total int throws invalid-report-entry; entries map of string, int
  total = 0
  for entry-name, units in entries
    require-entry; entry-name, units
    total = total + units
  return total

function progress-label string; total int, target int
  if total >= target
    return 'target met'
  return 'target not met'

function print-report; title string, target int, entries map of string, int
  total = strict-total; entries
  print; title
  for entry-name, units in entries
    print; '- ', entry-name, ': ', units
  print; 'Total units: ', total
  print; 'Progress: ', (progress-label; total, target)
```

Only `progress-label` and `print-report` are public. The validation and aggregation helpers remain implementation details of the reporting namespace.

### `app/main.trn`

```terrane
namespace work-report/app

from /core/collections import map
from /work-report/errors import invalid-report-entry
from /work-report/reporting import print-report as show-report

function main;
  unchecked map of string, int = map; design = 6, implementation = 9, cleanup = -2
  try
    show-report; 'Unchecked report', 18, unchecked
  catch invalid-report-entry
    print; 'Report rejected: correct the input and try again'
  finally
    print; 'Unchecked report attempt finished'

  corrected map of string, int = map; design = 6, implementation = 9, review = 5
  show-report; 'Corrected report', 18, corrected
```

The application imports the throwable type because its catch clause names that contract. It aliases `print-report` to the locally natural imperative `show-report`. The alias is optional; it demonstrates that local spelling and semantic identity are distinct.

Run the package:

```console
terrane run .
```

It produces the same behavior as Chapter 7:

```text
Report rejected: correct the input and try again
Unchecked report attempt finished
Corrected report
- design: 6
- implementation: 9
- review: 5
Total units: 20
Progress: target met
```

The output is unchanged because organization is not behavior. What has improved is the visible dependency graph:

```text
work-report/app
├── work-report/errors
└── work-report/reporting
    └── work-report/errors
```

The application chooses recovery. Reporting owns validation and presentation. The error namespace owns the failure contract. Private helpers prevent the application from reaching through that design and coupling itself to `strict-total`.

## Terrane style: let namespace boundaries follow responsibility

A namespace should name a coherent part of the program, not become a miscellaneous drawer. `work-report/reporting` makes a meaningful promise. Names such as `work-report/helpers`, `work-report/common`, or `work-report/misc` postpone the design question rather than answer it.

Prefer selective imports when they make dependencies legible. Use aliases to resolve a genuine collision or make a foreign name fit the local sentence—not to give every imported object a second decorative spelling.

Keep manifests explicit and source trees unsurprising. A reader should be able to move from namespace path to mapped directory without searching the entire repository. The compiler enforces that correspondence because project organization is part of reproducible program identity.

Most importantly, do not let file boundaries invent abstractions the program does not possess. We split the reporting tool along responsibilities already present in its one-file design. The package structure reveals those contracts; it does not manufacture them.

## What we learned

Namespaces give declarations stable, exact, slash-separated identities. Imports bind public objects into a lexical scope, selective aliases change local spelling without changing identity, and namespace-wide imports deliberately expose a broader public vocabulary.

A package manifest bounds source discovery and maps namespace roots to relative directory roots. The compiler verifies that source declarations match their locations, discovers mapped `.trn` files deterministically, and rejects undeclared or ambiguous structure. Direct source files remain implicit single-file packages using the same pipeline.

Visibility controls source-level access. Public declarations form the importable boundary; private helpers let a namespace change its implementation without inviting callers to depend on it. Dependency versions, features, capabilities, targets, and locks remain explicit build inputs rather than hidden runtime accidents.

The reporting tool now spans three files without changing behavior. Its application, domain error, and reporting responsibilities have become visible at package scale. In the next chapter, we will move from package organization to stateful domain modeling and distinguish classes, interfaces, traits, and protocols by the job each one performs.
