# 2. Values, Names, and Everyday Expressions

The first chapter gave us a working rhythm: edit a source file, check it, run it, and compare the result with what we expected. We can now slow down and examine the pieces inside those first programs.

Most everyday computation begins with a small vocabulary:

- values such as numbers, truth values, and text;
- names that let us use those values again;
- operators that combine and compare them;
- members that expose information or behavior;
- calls that ask an object to do something.

Terrane keeps those pieces regular. A name by itself refers to an object. A dot selects one of the object's members. A semicolon invokes an object. Parentheses say exactly where a nested expression belongs.

By the end of this chapter, you will be able to read and write expressions such as:

```terrane
within-budget = total <= budget
summary = 'Item: '.concat; item, ', total: ', total
print; ('Characters: '.concat; item.length)
```

We will use inferred types throughout. Chapter 10 develops explicit type contracts; here, we want to see how much ordinary code can say without annotation ceremony.

## Numbers, truth values, and text

A value is a piece of information a Terrane program can compute, store, pass, compare, or display.

Three kinds appear constantly in small programs:

```terrane
42
true
'Terrane'
```

These are an integer, a truth value, and a string.

### Whole numbers

A whole-number literal is written with decimal digits:

```terrane
0
7
1200
```

A leading minus sign negates a number:

```terrane
-4
```

Underscores may separate digits when they improve readability:

```terrane
1_000
2_500_000
```

The underscores do not change the value.

Terrane's ordinary `int` represents exact signed integers. Its meaning does not change because a value grows beyond a machine register. The compiler may use progressively larger representations, but source arithmetic continues to describe mathematical integers rather than silently wrapping at a hidden boundary.

That is a valuable default, but not a promise that enormous numbers cost the same as small ones. Larger representations require more work and storage. Later chapters introduce fixed-width integer types for formats and native boundaries that require them.

### Decimal numbers

A literal with a fractional part denotes a decimal numeric constant:

```terrane
3.5
0.25
-12.75
```

Without another numeric context, Terrane uses its default `float`, currently the same canonical type as `float64`.

Integer and floating values are distinct. Terrane does not silently guess how to combine unrelated numeric value types:

```terrane
price = 7.5
quantity = 3
total = price * quantity       # rejected: float64 and int differ
```

You can keep an expression consistently floating when that is its intended model:

```terrane
start = 7.5
increase = 2.0
result = start + increase
```

Chapter 10 explains numeric destinations and conversions. For now, the useful rule is: choose values that belong to one numeric model instead of relying on an invisible coercion.

### Truth values

A `bool` has exactly two values:

```terrane
true
false
```

Comparisons produce truth values:

```terrane
7 < 10
4 == 4
'name' != 'other'
```

We can also give a comparison a name:

```terrane
within-budget = total <= budget
```

Chapter 3 uses these values to choose and repeat work.

### Text

Single-quoted text creates a `string`:

```terrane
'Hello'
'Terrane source is UTF-8 text.'
''
```

The final example is an empty string. A string represents Unicode text; it is not an interchangeable bag of arbitrary bytes. Terrane uses UTF-8 as its standard string representation—the dominant encoding of the modern web and a common default in contemporary terminals and development tools.

For the moment, we will compose short strings with `concat` and display them with `print`. Chapter 5 explores text, multiline literals, searching, splitting, encoding, and explicit text views in detail.

## Giving a value a name

A bare assignment gives a value a name when that name does not already resolve in the current scope:

```terrane
travellers = 3
message = 'Ready'
finished = false
```

Read these as bindings:

- `travellers` is bound to the integer value `3`;
- `message` is bound to the string value `'Ready'`;
- `finished` is bound to the boolean value `false`.

The compiler infers each value's type. The values remain typed even though the source does not repeat an obvious annotation.

A useful name communicates meaning rather than only representation:

```terrane
subtotal = 24
discount = 2
total = subtotal - discount
```

The calculation is easy to recover because the names describe its roles.

Terrane's library and documentation convention is kebab-case:

```terrane
items-ready = 12
maximum-retries = 3
```

Uppercase and underscores are legal for user declarations, but consistent kebab-case makes examples and ordinary Terrane code easier to scan.

Terrane names are governed by Terrane's grammar, not by the implementation language used by the
compiler. Words such as `box`, `final`, and `override` remain legal ordinary names even though Rust
reserves them. Generated Rust safely encodes those spellings rather than imposing an extra source
restriction. Prefer names that communicate the program's domain; legality alone does not make a
general word descriptive.

### Names are read from their scope

Inside `main`, a name becomes available after its declaration:

```terrane
function main;
  first = 10
  second = first + 5
  print; second
```

The initializer for `second` can use `first` because `first` is already bound in the surrounding function body.

A name is not text. Writing `second` asks the current scope which object that name denotes; writing `'second'` creates a string containing six letters:

```terrane
print; second       # displays 15
print; 'second'     # displays the word second
```

## Changing a binding

When a bare assignment finds an existing mutable binding, it changes that binding:

```terrane
remaining = 10
remaining = remaining - 3
print; remaining
```

The output is:

```text
7
```

The right side is evaluated using the current value of `remaining`. The resulting value is then assigned back to the existing binding.

This distinction between a **binding** and its **value** is useful:

```terrane
score = 10
score = score + 5
```

The integer value `10` did not mutate into `15`. The name `score` now refers to the result of a new expression.

Terrane's compiler tracks which storage genuinely changes. You do not need to decorate every local binding with a mutability keyword before using ordinary reassignment.

Numeric bindings also support update statements:

```terrane
count = 1
count++
count--
```

`++` and `--` are complete statements. They do not produce expression values:

```terrane
next = count++       # rejected
```

This avoids the sequencing puzzles created when one expression both observes and updates a value. Write the two operations when both are needed:

```terrane
current = count
count++
```

Ordinary assignment has broader value-semantics consequences for collections and objects. Chapters 5 and 11 introduce those consequences when we have values substantial enough to make them visible.

## Arithmetic and comparisons

Terrane provides the familiar everyday arithmetic operators:

| Operator | Meaning |
|---|---|
| `+` | addition |
| `-` | subtraction |
| `*` | multiplication |
| `/` | division |
| `%` | remainder |

For example:

```terrane
width = 8
height = 5
area = width * height
perimeter = width * 2 + height * 2
```

Multiplication, division, and remainder bind more tightly than addition and subtraction:

```terrane
result = 2 + 3 * 4       # 14
```

Use parentheses when you want another grouping or when they make intent easier to see:

```terrane
result = (2 + 3) * 4     # 20
```

Integer division produces an integer quotient:

```terrane
print; 7 / 3             # 2
print; 7 % 3             # 1
```

Terrane defines signed integer division consistently using Euclidean quotient and remainder. In particular, a nonzero divisor produces a nonnegative remainder:

```terrane
print; -7 / 3            # -3
print; -7 % 3            # 2
```

You do not need these negative cases every day, but the result is a language contract rather than whatever the target machine happens to do.

### Comparisons

Comparisons produce booleans:

| Operator | Meaning |
|---|---|
| `==` | equal in value |
| `!=` | not equal in value |
| `<` | less than |
| `<=` | less than or equal |
| `>` | greater than |
| `>=` | greater than or equal |

Examples:

```terrane
same = 12 == 12
has-room = used < capacity
over-limit = total > maximum
```

Comparisons do not chain:

```terrane
minimum < value < maximum       # rejected
```

Write each relationship explicitly:

```terrane
minimum < value and value < maximum
```

Chapter 3 develops `and`, `or`, and `not` while building decisions.

### Precedence is a tool, not a puzzle

The compiler has precise precedence rules, but readable code should not make a reader reconstruct a long operator table. This is easy to follow:

```terrane
total = unit-price * quantity - discount
```

When several kinds of comparison, boolean, and arithmetic operators meet, parentheses can communicate the intended stages:

```terrane
acceptable = (total <= budget) and (quantity > 0)
```

Use grouping to reveal meaning, not to surround every literal mechanically.

## Member access with `.`

Values expose members. A dot selects one of them:

```terrane
item.length
```

Here, `item` is the receiver and `length` is the selected member. For a string, `length` reports the number of user-perceived characters, or grapheme clusters.

```terrane
item = 'notebook'
print; item.length
```

The output is:

```text
8
```

Member access has no whitespace before the dot:

```terrane
item.length       # member selection
item .length      # not the member form
```

The dot has one job in Terrane: it appears between a receiver and an instance member. It is not used as a namespace prefix or general punctuation for unrelated language features.

### Properties and methods

Some members are properties. Selecting one directly observes state, metadata, or classification:

```terrane
item.length
```

Other members are methods. Selecting a method produces a callable object; invoking it requires `;`:

```terrane
item.concat; ' case'
```

Parameter count does not decide the distinction. A zero-argument property needs no semicolon, while a zero-argument method still does:

```terrane
measurement.finite          # property
measurement.absolute;       # method call
```

This may feel precise for a first encounter, but it gives member syntax a dependable reading rule: dot selects; semicolon invokes.

## Calling with `;`

A semicolon invokes an object's default behavior:

```terrane
print; 'Hello'
```

In this case, `print` names a function object. The semicolon invokes it, and the string is its argument.

Calls may take several comma-separated arguments:

```terrane
print; 'Total: ', total, ' credits'
```

`print` displays them from left to right, then appends a newline.

A zero-argument call still includes the marker:

```terrane
refresh;
```

The semicolon is not a statement terminator. Newlines normally end statements. It specifically says **invoke the object on the left**.

The distinction is visible with methods too:

```terrane
result = text.trim;
```

The dot selects `trim`; the semicolon invokes it.

### The call owns the remaining expression

An unwrapped call extends through the rest of its logical expression:

```terrane
message = 'Item: '.concat; item, ', total: ', total
```

The call to `concat` receives three arguments: `item`, the middle string, and `total`. Its result is assigned to `message`.

Likewise:

```terrane
print; 2 + 3, ' is the result'
```

passes two arguments to `print`: the result of `2 + 3`, and the string.

This trailing form keeps common calls light. It also makes nested calls something we must delimit explicitly.

## Nested calls and parentheses

Suppose we want to compose a message and pass the result directly to `print`. This contains one call inside another:

```terrane
print; ('Hello, '.concat; name, '!')
```

The parentheses delimit the inner call. Read from the inside out:

1. select `concat` from `'Hello, '`;
2. invoke it with `name` and `'!'`;
3. pass the resulting string to `print`.

Without grouping, an unwrapped call owns the remainder of its logical expression. Terrane therefore rejects ambiguous ungrouped nested invocation rather than guessing where one argument list ends.

Parentheses can also make a member call's result one operand in a larger expression:

```terrane
long-enough = (prefix.concat; suffix).length >= 8
```

Or one argument among several:

```terrane
print; 'Message: ', (prefix.concat; suffix), ' ready'
```

Grouping does not itself invoke anything. The semicolon remains the call marker inside the parentheses.

### Passing a callable is not calling it

A bare name refers to its object and never invokes through adjacency:

```terrane
handler = render
```

Here, `render` is passed or stored as an object. To invoke it, write:

```terrane
result = render; report
```

To invoke it inside another call, group it:

```terrane
print; (render; report)
```

Function values become a practical tool in Chapter 4. For now, notice that the source always shows whether a callable is merely selected or actually invoked.

## Comments and readable layout

A `#` begins a line comment:

```terrane
# Calculate the remaining budget.
remaining = budget - total
```

A comment may also follow source on the same line:

```terrane
spare-bottles = 1      # One bottle for the guide.
```

Terrane also recognizes `//` line comments and `/* ... */` block comments, which can be useful around projected or native-adjacent source. Ordinary Terrane examples prefer `#` because it is visually light and does not resemble an arithmetic operator. Python readers may be relieved to see actual block comments. No string literals were harmed in the making of this paragraph.

Comments should explain information the code cannot state economically. This adds useful context:

```terrane
# The venue charges in whole credits; no fractional currency is used.
unit-price = 8
```

This merely repeats the expression:

```terrane
unit-price = 8         # Set unit-price to 8.
```

Names and layout should carry most local meaning.

### Indentation and blank lines

Indentation defines blocks. Within one block, align sibling statements:

```terrane
function main;
  subtotal = 24
  discount = 2
  total = subtotal - discount
  print; total
```

Blank lines do not create scope. They separate conceptual stages for readers:

```terrane
subtotal = unit-price * quantity
total = subtotal - discount

within-budget = total <= budget

print; 'Total: ', total
print; 'Within budget: ', within-budget
```

Use compact groups where statements belong together and one blank line where the program changes subject. Excess vertical space can obscure relationships just as surely as a wall of uninterrupted source.

## Everything is an object—semantically

Numbers, booleans, strings, functions, methods, classes, namespaces, collections, errors, and tasks are all objects in Terrane's source-language model.

That statement explains why the same surface ideas recur:

- a name resolves to an object;
- `.` selects an object's member;
- `;` invokes an object's default behavior;
- objects participate in typed protocols.

An integer can therefore expose arithmetic behavior, a string can expose `length` and `concat`, and a function can be selected, passed, or invoked.

“Everything is an object” does **not** mean every value is heap allocated, boxed into one universal representation, or dispatched through a runtime method table. The compiler may lower:

```terrane
answer = 42
```

to an ordinary native integer representation when that preserves all observable behavior.

The object model describes what source code can observe. Runtime representation is an optimization and lowering decision. Keeping those levels separate lets Terrane provide a uniform language without charging every value for machinery it does not need.

Chapter 9 uses this model to introduce user-defined classes, interfaces, and traits. The everyday lesson is simpler: built-in values are not second-class exceptions to member and call syntax.

## Why Terrane: why calls use `;`

Many languages call a function with parentheses:

```text
print(message)
```

Others use whitespace or juxtaposition in some contexts. Terrane gives invocation its own marker:

```terrane
print; message
```

This choice serves three related goals.

First, it separates **referring to an object** from **invoking it**:

```terrane
operation = render          # keep the callable object
result = render; report     # invoke it
```

There is no special exception for zero arguments. `refresh` selects an object; `refresh;` invokes it.

Second, it leaves the common argument list visually open:

```terrane
print; 'Total: ', total, ' credits'
```

Most calls need no enclosing punctuation around the whole list.

Third, it composes with member selection using one stable reading order:

```terrane
text.trim;
```

Dot selects `trim`; semicolon invokes the selected object.

The tradeoff is also explicit. Because a trailing call owns the rest of its logical expression, nested calls require parentheses:

```terrane
print; (render; report)
```

That is not accidental ceremony. It marks the boundary that an outer pair of mandatory call parentheses would have supplied in another language.

The aim is not to make Terrane look unusual for its own sake. It is to keep selection, passing, and invocation distinct while allowing frequent calls to remain light. A good Terrane expression should be readable with one mechanical rule:

> Names and dots select objects; semicolons invoke them; parentheses delimit nesting.

We will keep testing that rule as calls grow more capable in later chapters.

## Project: calculate a small purchase

We can now revisit the packing-style arithmetic from Chapter 1 with a slightly richer program. Create `everyday-expressions.trn`:

```terrane
namespace everyday-expressions

function main;
  item = 'notebook'
  unit-price = 8
  quantity = 3
  subtotal = unit-price * quantity
  discount = 2
  total = subtotal - discount
  budget = 25
  within-budget = total <= budget

  summary = 'Item: '.concat; item, ', total: ', total
  print; summary
  print; 'Within budget: ', within-budget
  print; 'Characters in item: ', item.length

  remaining = budget
  remaining = remaining - total
  print; 'Budget remaining: ', remaining
```

Run it:

```console
terrane run everyday-expressions.trn
```

It prints:

```text
Item: notebook, total: 22
Within budget: true
Characters in item: 8
Budget remaining: 3
```

The program separates its work into three stages.

First, it binds the inputs and computes derived values:

```terrane
subtotal = unit-price * quantity
discount = 2
total = subtotal - discount
budget = 25
within-budget = total <= budget
```

Second, it selects the string's `concat` method and calls it to build a summary:

```terrane
summary = 'Item: '.concat; item, ', total: ', total
```

Third, it selects properties, calls `print`, and updates a binding:

```terrane
print; 'Characters in item: ', item.length
remaining = budget
remaining = remaining - total
```

No explicit type annotation was needed, but every operation was checked against the inferred value types. The code also contains no import lines: `print` and type construction vocabulary are available without them, while this program does not yet use an operational collection facility.

## What we learned

Terrane programs compute with typed values even when local annotations are inferred. Whole numbers use exact `int` semantics, decimal values use the default floating type without another context, booleans are `true` or `false`, and strings hold Unicode text.

A bare assignment introduces a binding when its name is unresolved and updates an existing mutable binding when one is already visible. Arithmetic combines compatible numeric values; comparisons produce booleans. Parentheses override precedence and communicate grouping.

Member access and invocation remain separate:

```terrane
item.length                  # select a property
item.concat; ' case'         # select and invoke a method
print; item                  # invoke a function object
print; (render; report)      # delimit a nested call
```

Everything participates in one semantic object model, but the compiler remains free to use specialized native representations. The explicit semicolon keeps object selection, callable passing, and invocation visibly distinct.
