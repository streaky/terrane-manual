# 5. Text and Collections

Programs become useful when they can work with more than one isolated value. Text contains characters and words. A list preserves a sequence. A map associates keys with values. Iteration lets functions process those structures without knowing their runtime representation.

Terrane treats these as ordinary typed objects with value semantics. Assignment gives the destination an independent logical value, while the compiler and runtime may share backing storage until a mutation requires separation. The programmer gets predictable behavior without demanding an eager deep copy after every assignment.

In this chapter, we will:

- write quoted, tail, and block text;
- use common string operations;
- understand bytes, Unicode scalars, and grapheme clusters;
- create, index, append to, and iterate over lists;
- create, update, look up, and iterate over maps;
- build collections from existing values;
- choose a collection that matches the program's question;
- observe ordinary copy-on-write value behavior;
- build a small word-frequency program.

The examples use `string`, `list`, and `map`. Chapter 10 will examine their type relationships more formally; here, we will use their everyday behavior.

## Quoted, tail, and block text

The quoted strings used so far are ideal for short text:

```terrane
greeting = 'Hello, Terrane!'
empty = ''
```

A quoted string begins and ends with `'`. Escape sequences represent characters that would otherwise interfere with the literal:

```terrane
apostrophe = 'It\'s ready.'
path = 'one\\two'
lines = 'first\nsecond'
```

The source spelling and resulting text are not always identical. `\'` contributes one apostrophe, `\\` contributes one backslash, and `\n` contributes a newline.

Terrane also provides text forms that avoid escape punctuation when the source already has the shape we want.

### Tail text

`>` captures the rest of the logical line as text:

```terrane
message = >This text continues to the end of the line.
```

The literal needs no closing delimiter. Its content begins immediately after `>` and ends at the logical newline. Because `return` begins a result expression, `return >ready` returns tail text directly.

Tail text is useful for shell fragments, regular expressions, templates, or punctuation-heavy examples:

```terrane
pattern = >^[a-z][a-z0-9-]*$
example = >Call with: render; report
```

Backslashes and quotes are ordinary content in tail text. Because the rest of the line belongs to the literal, nothing after it is parsed as Terrane source.

Use quoted text when the closing boundary helps a larger expression:

```terrane
message = 'Hello'.concat; ', ', name
```

Use tail text when the remainder of one line is simply the text itself.

### Block text

`>>` introduces an indented block of literal text:

```terrane
message = >>
  First line
  Second line
  Third line
```

The common structural indentation is removed. The content is therefore:

```text
First line
Second line
Third line
```

No implicit final newline is added. A blank content line remains a blank line, while dedenting to the surrounding source indentation ends the block.

Inside a function, the source structure remains visible:

```terrane
function main;
  message = >>
    Packing report
    --------------
    Ready to leave
  print; message
```

The content lines are indented farther than the assignment because they belong to the block literal. The same rule permits `return >>` followed by an indented text block. `print` returns to the function body's indentation and is therefore ordinary Terrane source again.

Block text is useful for messages, test inputs, generated configuration, and small templates. It should not become a hiding place for another language when a structured Terrane representation would be clearer.

### Choose the form that removes noise

These forms produce text through different source boundaries:

| Form | Best fit |
|---|---|
| `'quoted text'` | short text embedded in an expression |
| `>tail text` | punctuation-heavy remainder of one line |
| `>>` block | multiline text whose layout matters |

Choose the form that lets the reader see the content rather than the escaping mechanism.

## Common string operations

A `string` is a Unicode text value. Its members provide common transformations and questions.

### Concatenation and joining

`concat` appends the canonical display of each argument to the receiver:

```terrane
name = 'Ada'
message = 'Hello, '.concat; name, '!'
```

The result is:

```text
Hello, Ada!
```

`join` places the receiver between supplied values:

```terrane
line = ', '.join; 'red', 'green', 'blue'
```

The result is:

```text
red, green, blue
```

Use `concat` when one string grows around adjoining pieces. Use `join` when one separator belongs between a sequence of values.

Both operations produce new strings. They do not mutate the receiver:

```terrane
prefix = 'Hello'
message = prefix.concat; ', world'
print; prefix
```

`prefix` still contains `Hello`.

### Case, trimming, searching, and replacing

Common method families include:

```terrane
lower = text.lower;
upper = text.upper;
trimmed = text.trim;
has-word = text.contains; 'Terrane'
changed = text.replace; 'old', 'new'
parts = text.split; ','
```

Case conversion follows Unicode-aware behavior. `trim` removes the text operation's defined surrounding whitespace. `contains` answers a boolean question. `replace` and `split` produce new values.

Method families may later expose policy variants as child members. The ordinary spelling chooses the family's default behavior:

```terrane
text.lower;
text.trim;
```

Later chapters examine member families and protocol contracts directly. For now, use the default operation whose name states the intended text transformation.

### Length

A string's default `length` counts grapheme clusters:

```terrane
print; 'notebook'.length       # 8
```

A grapheme cluster corresponds closely to what a user perceives as one character. That default makes text length useful for interfaces, labels, and human-facing limits rather than exposing an encoding detail accidentally.

When bytes or Unicode scalar values are the real subject, request those views explicitly.

## Bytes, Unicode scalars, and grapheme clusters

The word “character” can mean several different things in software.

Consider `é`. It may be represented as one precomposed Unicode scalar, or as the scalar `e` followed by a combining acute accent. Those spellings can look identical to a person while containing different scalar sequences and byte sequences.

Terrane therefore gives text three explicit views:

```terrane
text.bytes
text.scalars
text.graphemes
```

- `bytes` exposes the UTF-8 encoded bytes;
- `scalars` exposes Unicode scalar values;
- `graphemes` exposes user-perceived text elements.

The default string operations are grapheme-oriented where a character boundary matters. Iterating a string follows its grapheme view:

```terrane
for character in text
  print; character
```

This keeps a combining sequence together as one item.

### Ask the question at the right level

Use bytes when implementing an encoded format, checksum, transport, or native boundary:

```terrane
encoded = text.bytes
```

Use scalars when the algorithm is defined in Unicode code points:

```terrane
for scalar in text.scalars
  print; scalar
```

Use graphemes for user-facing editing and iteration:

```terrane
for character in text.graphemes
  print; character
```

And use the string directly when its default grapheme iteration is what you mean:

```terrane
for character in text
  print; character
```

The explicit views prevent byte length, scalar count, and visible-character count from being mistaken for interchangeable answers.

### Indexing binary data

Index a byte sequence with an integer when you need one octet. The result is a `uint8`, not a
one-character string:

```terrane
first-byte uint8 = encoded[0]
```

Use a range object to select bytes. The result remains `bytes`, and the range's step and
half-open or inclusive end are honored:

```terrane
from /core/collections import range

header bytes = encoded[range; 0, 4]
alternating bytes = encoded[range; 0, encoded.length, 2]
```

An invalid selected index throws `index-error`. A range with equal start and end at a valid
boundary produces empty bytes. Neither operation guesses text boundaries; decode explicitly when
the selected bytes are meant to be text.

### Encoding is a boundary

A string is Unicode text, while `bytes` is binary data. Crossing between them requires an encoding policy:

```terrane
encoded = text.encode; utf8
decoded = encoded.decode; utf8
```

`utf8` is available from the default prelude. Decoding validates the bytes rather than silently manufacturing text from invalid input.

This separation is why strings are not arbitrary byte bags. Text algorithms can operate on text guarantees, while binary protocols remain free to contain any byte values.

## Creating lists

A list stores an ordered sequence of values. Import its constructor from `/core/collections`:

```terrane
from /core/collections import list
```

Create a populated list by calling `list`:

```terrane
colours = list; 'red', 'green', 'blue'
```

The compiler infers `list of string` because every supplied item is a string.

An empty list needs an annotation to say what it will contain:

```terrane
colours list of string = list
```

Without an item, the constructor alone cannot infer the intended element type.

Lists preserve order and allow duplicates:

```terrane
votes = list; 'red', 'blue', 'red'
```

Their `length` property reports the number of elements:

```terrane
print; votes.length       # 3
```

### Indexing

List indices begin at zero:

```terrane
colours = list; 'red', 'green', 'blue'
print; colours[0]         # red
print; colours[2]         # blue
```

Ordinary indexing requires a valid index. An invalid index raises an `index-error`; it does not return a fabricated default value.

When absence is expected, use the checked lookup family:

```terrane
possible = colours.get.checked; 10
```

The result is the item or `none`. Chapter 10 develops unions and narrowing, and Chapter 7 develops the error path of required lookups.

### Appending and replacing

Append a value with:

```terrane
colours.append; 'yellow'
```

Replace an element through indexed assignment:

```terrane
colours[1] = 'emerald'
```

or through the explicit method:

```terrane
colours.set; 1, 'emerald'
```

All inserted values must satisfy the list's element type. A `list of string` cannot accept an integer simply because one call attempts it.

These operations are observable mutations of the list binding, but they retain Terrane's ordinary value semantics when the list has previously been assigned elsewhere. We will examine that shortly.

## Iterating over lists

A list is iterable:

```terrane
for colour in colours
  print; colour
```

Items arrive in list order. The loop target is an ordinary local value; assigning to it does not replace the corresponding list element.

To build a transformed list, make the destination explicit:

```terrane
names = list; 'ada', 'grace', 'barbara'
upper-names list of string = list

for name in names
  upper-names.append; (name.upper;)
```

Now `upper-names` contains the uppercase strings while `names` remains unchanged.

This is intentionally direct. The source identifies:

- the input collection;
- the operation applied to each item;
- the destination collection;
- the order in which results are appended.

Later library abstractions may package common transforms, but an ordinary loop is not a second-class or inherently interpreted fallback. It lowers through the native compiler pipeline.

### Iteration observes a snapshot

A collection loop iterates a snapshot taken when the loop begins. Mutating the original binding inside the body does not alter the sequence already being visited:

```terrane
values = list; 1, 2, 3
for value in values
  values.append; value + 10
```

The loop visits the original three items, then ends. `values` contains six items afterward. It does not chase the newly appended tail forever.

Snapshot iteration makes mutation during traversal deterministic, though building a separate result list is often clearer when transformation is the goal.

## Creating and updating maps

A map associates unique keys with values and preserves insertion order. Import its constructor:

```terrane
from /core/collections import map
```

A convenient constructor form uses identifier-like string keys:

```terrane
counts = map; red = 2, blue = 3
```

This creates the string keys `'red'` and `'blue'`.

For an empty map, state both key and value types:

```terrane
counts map of string, int = map
```

Insert or replace a value with `set`:

```terrane
counts.set; 'red', 2
counts.set; 'blue-green', 1
```

`set` accepts arbitrary values satisfying the map's key and value types, so it is not limited to identifier-like text keys.

### Looking up a value

Index with a key when the key is required to exist:

```terrane
print; counts['red']
```

A missing required key raises `missing-key` rather than returning an unrelated default.

Use checked lookup when absence is an expected outcome:

```terrane
possible = counts.get.checked; 'violet'
if possible == none
  print; 'No violet count'
```

This makes the policy visible at the call site: ordinary indexing requires the item, while `get.checked` admits absence as data.

### Iterating over a map

A map yields key and value pairs in insertion order:

```terrane
for colour, count in counts
  print; colour, ': ', count
```

Updating an existing key changes its value without moving it to a new insertion position. Adding a new key places it at the end.

Maps also expose ordered views:

```terrane
keys = counts.keys;
values = counts.values;
entries = counts.entries;
```

An entry exposes `.key` and `.value` properties. The paired loop form is usually clearest when both are needed immediately.

Insertion order is a semantic guarantee of `map`, not an accident of one runtime hash table. An explicitly unordered map exists for programs whose contract does not require order.

## Building collections from existing values

Collections often arise from a loop rather than one constructor call.

We can collect the nonempty words from a string by iterating its graphemes and appending completed words:

```terrane
words list of string = list
current-word = ''

for character in text
  if character == ' '
    if current-word != ''
      words.append; current-word
      current-word = ''
  else
    current-word = current-word.concat; character

if current-word != ''
  words.append; current-word
```

The final `if` handles a word not followed by a space.

The example deliberately states a small tokenization policy:

- spaces separate words;
- repeated spaces do not create empty words;
- punctuation remains part of a word;
- Unicode graphemes stay intact.

A production tokenizer may need richer rules, but those rules should be explicit rather than concealed behind the vague instruction “split into words.”

### Building ordered unique values

A list preserves duplicates. To construct a small ordered list of unique words, compare each candidate with the values already retained:

```terrane
unique-words list of string = list

for word in words
  seen = false
  for known-word in unique-words
    if known-word == word
      seen = true
  if not seen
    unique-words.append; word
```

This simple nested loop is not the most efficient uniqueness algorithm for a large input, but it makes the policy and insertion order obvious. A `set` is the natural scalable collection when membership is the central operation.

### Building a map from calculated pairs

Once we have unique words, we can count each one and store the result:

```terrane
counts map of string, int = map

for unique-word in unique-words
  count = 0
  for word in words
    if word == unique-word
      count++
  counts.set; unique-word, count
```

The outer loop determines insertion order. The inner loop calculates the value associated with each key. The map then provides keyed lookup and ordered reporting.

This version favors visible steps over an optimized counting strategy. The project at the end of the chapter uses it because every operation has already been introduced. The next section shows how checked lookup can reduce repeated work while preserving the same observable result.

### Refactoring to one pass after measurement

For a larger input, the repeated scans may become the dominant cost. The map can answer the
same question while each word is visited:

```terrane
counts map of string, int = map

for word in words
  current = counts.get.checked; word
  if current != none
    counts.set; word, current + 1
  else
    counts.set; word, 1
```

`get.checked` makes a missing first occurrence ordinary: it returns `none` rather than throwing.
In the first branch, the check has refined `current` to `int`, so arithmetic is valid. Updating an
existing key retains its insertion position, and inserting a new key records its first-seen
position. The one-pass form therefore preserves the report's order while avoiding the nested
counting scans.

This is a refactoring, not an automatic replacement for the transparent version. Begin with the
form that makes the intended result easy to verify, measure the relevant workload, then choose the
more direct collection operation when the difference matters.

## Choosing the right collection

Choose a collection according to the question the program asks.

### List: sequence and position

Use a list when order, position, or duplicates matter:

```terrane
steps = list; 'measure', 'cut', 'assemble'
```

Questions include:

- What is the next item?
- What is at index two?
- In what order should these values be processed?

### Map: association by key

Use a map when one value is retrieved or updated by another value:

```terrane
scores map of string, int = map
scores.set; 'Ada', 10
```

Questions include:

- What score belongs to this name?
- Has this key received a value?
- Which key-value pairs should be reported?

### Set: membership and uniqueness

Use a set when membership is the primary question and duplicates have no meaning:

```terrane
from /core/collections import set
seen set of string = set
seen.add; 'red'
```

Questions include:

- Have we seen this value?
- Which distinct values occur?
- Should this value be added or removed?

### Tuple: fixed position and shape

Use a tuple when a small, fixed set of positions forms one value:

```terrane
coordinate = (3, 5)
```

A tuple is not a list whose length happens to remain unchanged. Its fixed positional shape is part of its type.

### Prefer the narrowest honest meaning

A map with integer keys can imitate a list, and a list can be repeatedly scanned to imitate a map or set. Choose the collection whose operations state the domain directly. Doing so gives both readers and the compiler better information.

## Assignment and copy-on-write value behavior

Terrane assignment gives the destination an independent logical value:

```terrane
original = list; 'red', 'green'
copy = original
copy.append; 'blue'

print; original.length       # 2
print; copy.length           # 3
```

Mutating `copy` does not mutate `original`.

The same rule applies to maps:

```terrane
original = map; red = 1
copy = original
copy.set; 'blue', 2

print; original.length       # 1
print; copy.length           # 2
```

This is value behavior. It does not require the runtime to eagerly duplicate every element at assignment. Terrane may let both values share backing storage while neither changes. The first relevant mutation separates the changed value through copy-on-write.

The optimization is intentionally unobservable. Source code can rely on independence, not on whether a particular assignment allocated.

### Iteration follows the same model

Because a `for` loop observes a collection snapshot, later mutation of the original binding cannot retroactively alter the items already selected for that traversal. Value semantics and snapshot iteration reinforce the same principle: a local operation should not acquire surprising shared effects merely because storage was optimized underneath it.

When shared changing identity is the actual model, Chapter 11 introduces explicit references. Ordinary collections do not smuggle that identity through assignment.

## Why Terrane: values without accidental aliasing

Mutable collections are convenient. Shared storage is efficient. Combining them carelessly creates one of programming's most persistent surprises: changing one apparently local value changes another distant value because both names secretly refer to the same mutable object.

Terrane separates the source contract from the storage optimization.

At the source level:

```terrane
second = first
second.append; value
```

means that `second` may change while `first` retains its value.

Underneath, the compiler may use shared backing storage and copy-on-write to avoid unnecessary eager duplication. If analysis proves a sequence of mutations uniquely owned, it may establish uniqueness once and lower the operations directly. The runtime representation is free to become efficient; the visible value behavior remains stable.

This gives ordinary code a useful default:

- assignment does not create accidental shared mutation;
- functions receive values rather than hidden aliases;
- collection traversal observes a stable snapshot;
- deliberate shared identity remains expressible through explicit reference types later.

The principle is not that mutation is bad. Lists and maps are designed to change. The principle is that **mutation should affect the value the source visibly names**, unless the program explicitly chooses a shared identity model.

This is also a performance contract worth inspecting rather than trusting blindly. Chapter 13 will show generated Rust, and later performance work will follow collection operations through lowering and runtime support. Value semantics describe the required behavior; they do not excuse avoidable copies, repeated ownership checks, or hidden allocation.

## Project: word frequency

We will combine text iteration, list construction, ordered uniqueness, and a map into a small word-frequency program.

Create `word-frequency.trn`:

```terrane
namespace word-frequency

from /core/collections import list, map

function main;
  text = 'Red blue red green blue blue'.lower;
  words list of string = list
  current-word = ''

  for character in text
    if character == ' '
      if current-word != ''
        words.append; current-word
        current-word = ''
    else
      current-word = current-word.concat; character

  if current-word != ''
    words.append; current-word

  unique-words list of string = list
  for word in words
    seen = false
    for known-word in unique-words
      if known-word == word
        seen = true
    if not seen
      unique-words.append; word

  counts map of string, int = map
  for unique-word in unique-words
    count = 0
    for word in words
      if word == unique-word
        count++
    counts.set; unique-word, count

  print; 'words: ', words.length
  for word, count in counts
    print; word, ': ', count
```

Run it:

```console
terrane run word-frequency.trn
```

It prints:

```text
words: 6
red: 2
blue: 3
green: 1
```

The program has four visible stages.

First, it normalizes case:

```terrane
text = 'Red blue red green blue blue'.lower;
```

Without that step, `'Red'` and `'red'` would be distinct map keys.

Second, it tokenizes the string into a list. The loop treats spaces as separators and appends each completed nonempty word.

Third, it builds `unique-words` in first-seen order. This determines the later map's insertion order.

Fourth, it counts each unique word and inserts the pair into `counts`. Map iteration then reports the entries in deterministic order.

This is intentionally a transparent first implementation rather than the fastest possible frequency counter. Every pass has a clear job, and the program's output policy is easy to inspect. If a larger input makes the nested counting expensive, measurement can justify a more direct checked-lookup or set-based design. The clear implementation remains a useful reference for testing the optimized one.

## Terrane style: make data shape visible

A collection declaration should tell the truth about the role of its data:

```terrane
words list of string = list
counts map of string, int = map
```

The annotations are necessary for empty constructors and useful to readers: one value is an ordered sequence of words; the other associates words with counts.

Prefer direct operations whose names preserve that shape:

```terrane
words.append; word
counts.set; word, count
```

Avoid encoding association through matching positions in two unrelated lists unless positional correspondence is genuinely the domain model.

Likewise, request the text view the algorithm means. A user-facing loop should not iterate bytes merely because UTF-8 is the storage representation. A binary protocol should not pretend arbitrary bytes are a string.

The recurring question is:

> What structure and boundary does the program actually mean?

Choosing the honest text view or collection usually makes the code clearer and gives the compiler stronger information at the same time.

## What we learned

Terrane offers quoted text for short expressions, tail text for the remainder of one line, and indented block text for multiline content. Strings provide Unicode-aware operations such as concatenation, joining, case conversion, trimming, searching, splitting, and replacement.

Text has distinct byte, scalar, and grapheme views. Default string length and iteration follow grapheme boundaries, while encoding and decoding make the text/binary boundary explicit.

Lists preserve ordered elements and duplicates. Maps associate unique keys with values and preserve insertion order. Both support mutation while retaining ordinary value behavior across assignment. The implementation may use copy-on-write storage, but one binding's mutation does not accidentally change an independent value.

Iteration visits a snapshot. Building a destination collection with a direct loop keeps transformations and ordering visible, while choosing list, map, set, or tuple according to the program's actual question prevents representation tricks from becoming domain design.
