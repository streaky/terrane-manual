# 12. Asynchronous Work and Structured Concurrency

So far, every function in this book has completed one step before the caller continued to the next. That is often exactly what a program should do. Sequential code is easy to read, easy to test, and usually the clearest expression of a sequential problem.

Some work is different. A program may need to wait for several independent operations, keep making progress while one operation is suspended, or arrange for a group of operations to stop together when their result is no longer useful.

Terrane expresses that work with asynchronous functions and structured task scopes.

The most important word in that sentence is *structured*. Starting concurrent work is easy in many languages. Knowing when it ends, where its errors go, what owns its result, and whether it survives the code that started it is the harder problem. Terrane makes those questions part of the program's ordinary structure.

Chapter 11 gave us the ownership vocabulary for this structure. Task handles have one owner, `move` transfers that handle into the operation that consumes it, and references that cross a suspension must still have a living owner. Concurrency does not replace those rules; it gives them more work to do.

In this chapter, we will:

- declare and await an asynchronous function;
- start independent work in a task scope;
- join tasks and inspect their outcomes;
- handle failure and cancellation without losing track of work;
- place deadlines on scopes;
- see how executor profiles change execution without changing source semantics.

You do not need to think about operating-system threads to begin. An asynchronous function describes work that may suspend. The selected executor decides how tasks are driven. Terrane's source-level rules remain the same either way.

## When a program should be asynchronous

Asynchronous code is useful when a program has work that can make progress independently.

Typical examples include:

- waiting for several network responses;
- processing independent inputs;
- supervising a set of background operations for the lifetime of a request;
- applying one deadline to a group of related tasks;
- cancelling work whose result is no longer needed.

Asynchronous code is not automatically faster. Turning one calculation into a task does not make the calculation smaller, and immediately waiting for every task before starting the next one preserves the same basic sequence.

A useful first question is:

> Can something else make meaningful progress while this work is suspended?

If the answer is no, an ordinary function is probably clearer. If the answer is yes, an asynchronous function may describe the work more honestly.

We will begin with a deliberately small example so that the new mechanics are visible.

## Declaring and awaiting asynchronous work

Add `async` before `function` to declare an asynchronous function:

```terrane
namespace async-answer

async function answer int;
  return 42

async function main;
  value int = await answer;
  print; value
```

This program prints:

```text
42
```

The declaration:

```terrane
async function answer int;
```

looks like the function declarations from Chapter 4 with one additional promise: invoking `answer` creates asynchronous work.

The expression:

```terrane
await answer;
```

invokes `answer`, waits for that invocation to finish, and produces its `int` result. `await` is accepted inside an asynchronous function, so `main` is asynchronous here as well.

There are two distinct operations in that line:

1. `answer;` invokes the asynchronous function and creates a task.
2. `await` consumes that task and produces its result.

A task is a real value, even when the two operations are written together. We can separate them:

```terrane
task = (answer;)
value int = await task
```

The parentheses delimit the call so that the task produced by `answer;` can be assigned before `await` consumes it. This is the same call-grouping rule used elsewhere in Terrane; asynchronous calls do not introduce a second invocation grammar.

### Tasks are linear

An asynchronous invocation produces a **linear task**. A linear value must have one clear consumer. Awaiting the task consumes it:

```terrane
task = (answer;)
value = await task
```

The task cannot then be awaited again. More importantly, it cannot simply be forgotten:

```terrane
task = (answer;)
print; 'leaving without consuming task'
```

Terrane rejects the function because `task` reaches the end of its scope unconsumed.

This is not bookkeeping for its own sake. An abandoned task raises questions with no reliable local answer:

- Is it still running?
- Who observes its failure?
- What keeps its captured values alive?
- Should it be cancelled when the caller returns?

Terrane does not answer those questions by silently detaching the task. The program must consume the task, either by awaiting it directly or by managing scoped work through the task-scope operations introduced next.

### Await is a suspension point

An asynchronous function may suspend at `await`. While it is suspended, its executor may make progress on other work.

That has an ownership consequence. Values that remain live across the suspension must remain valid when execution resumes. Terrane checks that condition rather than treating every reference as safe merely because its source binding is textually nearby.

Most ordinary owned values require no special handling. Non-owning references deserve more care: the compiler must be able to prove that the owner survives the suspension and is valid in the selected execution context. If it cannot, the program is rejected at the relevant source locations.

The practical rule remains the one from Chapter 11:

> Prefer ordinary values. Carry a reference across suspension only when shared identity is genuinely required and its lifetime is clear.

Tasks also carry a compiler-inferred execution contract. A **transferable** task may be handed to an
executor that moves work between threads. A **local** task must remain on one executor thread. The
compiler derives that distinction from the callable's parameters, captures, values retained across
suspension, and the async operations it invokes.

This does not add a qualifier to ordinary source. Direct calls and immediate `await` keep their
concrete future representation. An asynchronous entrypoint enters one runtime selected by the
manifest profile; a projected Rust future is constructed when its Terrane call expression is
evaluated, before the generated async containment wrapper begins polling it. Pending dependency
timers and sockets sleep until their waker fires rather than being repeatedly polled.
The distinction between local and transferable work becomes visible when an operation such as
scoped spawn requires movement: the threaded profile rejects an executor-local
callable in source terms, while the cooperative profile can run it. Projected Rust async members are
conservatively local unless their admitted contract proves that the returned future is transferable.

## Task scopes

Direct `await` is enough when one asynchronous operation begins and the caller immediately needs its result. To run independent work under one lifetime, create a task scope:

```terrane
scope = task-scope;
```

A task scope owns the concurrent work started through it. It provides a boundary for spawning, joining, cancellation, and deadlines.

Here is a complete scoped example:

```terrane
namespace structured-task-scope

async function work int;
  return 42

async function main;
  scope = task-scope;
  child = scope.spawn; work
  outcome = await scope.join; child
  print; outcome.completed, outcome.cancelled
  value = outcome.value
  if value != none
    print; value
```

It prints:

```text
truefalse
42
```

Recall that `print` concatenates its arguments without inserting a separator. The first line therefore contains the two values `true` and `false` next to one another.

There are three new operations:

```terrane
scope = task-scope;
child = scope.spawn; work
outcome = await scope.join; child
```

We will take them one at a time.

## Spawning work within a scope

The call:

```terrane
child = scope.spawn; work
```

passes the asynchronous function `work` to the scope. It does **not** invoke `work` first. Compare the two forms:

```terrane
scope.spawn; work       # pass the callable for the scope to start
await work;             # invoke the callable, then await its task directly
```

The current scoped operation accepts a zero-argument asynchronous callable. The scope starts it and returns a scoped child-task value.

A scope may start more than one child before joining any of them:

```terrane
first = scope.spawn; first-work
second = scope.spawn; second-work
third = scope.spawn; third-work
```

Those children are independent pieces of work under the same structural owner. The selected executor may make progress on them concurrently.

Spawning several children before joining them is the important difference from immediately awaiting one call after another. This:

```terrane
first-value = await first-work;
second-value = await second-work;
```

finishes the first awaited invocation before the second invocation is consumed. This:

```terrane
scope = task-scope;
first = scope.spawn; first-work
second = scope.spawn; second-work
first-outcome = await scope.join; first
second-outcome = await scope.join; second
```

starts both children before waiting for their outcomes.

The order in which we join children does not claim that they completed in that order. It only controls the order in which this function observes their outcomes.

## Joining tasks and observing outcomes

A scoped child is consumed by `join`:

```terrane
outcome = await scope.join; child
```

The scoped child is statically non-copyable, so passing it to `join` transfers it automatically.
`join` constructs a task for observing the outcome, and `await` consumes that task. After the join,
`child` has been consumed and cannot be joined again. Lowering may express the transfer as a Rust
move without requiring a corresponding keyword in Terrane source.

Joining asynchronously returns an outcome rather than returning only the child's value. A task outcome exposes four observations:

- `completed`: whether the child completed successfully;
- `cancelled`: whether cancellation was requested or observed for the child;
- `value`: the successful result, or `none` when no result is available;
- `error`: the escaping error, or `none` when no error is available.

For a successful child:

```terrane
outcome = await scope.join; child
value = outcome.value
if value != none
  print; value
```

The comparison with `none` narrows the optional value before it is used. This is the same approach used for other finite alternatives: first establish which alternative is present, then use the value under that knowledge.

Do not infer success from `value` alone when the other outcome facts matter to your program. The outcome fields exist so that code can distinguish success, failure, and cancellation explicitly.

### Every scoped child must be joined

Starting work in a scope creates an obligation to account for it:

```terrane
scope = task-scope;
child = scope.spawn; work
```

Leaving the function here is rejected because `child` has not been consumed.

The valid form joins it:

```terrane
scope = task-scope;
child = scope.spawn; work
outcome = await scope.join; child
```

This rule remains in force when a scope contains several children. A failure in one child does not turn the others into detached work, and requesting cancellation does not remove the obligation to join them.

That gives task scopes their central structural guarantee:

> Work started in a scope remains owned and observable within that scope.

## Failure inside a task

Asynchronous functions use the same structured error model as ordinary functions. An asynchronous function may declare an escaping throwable contract and throw an error:

```terrane
namespace throwing-scoped-task
from /core/errors import throwable, coercion-error

async function fail int throws throwable;
  throw coercion-error

async function main;
  scope = task-scope;
  child = scope.spawn; fail
  outcome = await scope.join; child
  print; outcome.completed, outcome.cancelled, outcome.value == none
  print; outcome.error != none
```

This prints:

```text
falsefalsetrue
true
```

The child did not complete successfully, it was not cancelled in this example, it produced no value, and its outcome contains an error.

Notice where the failure appears. `scope.spawn; fail` starts the child; it does not throw the child's eventual error into `main` at that line. The failure is retained in the outcome observed by `join`.

This gives the supervising function a place to make a policy decision. It can inspect the outcome, report the error, cancel related work, or translate the failure into a different application-level result.

### One child failing affects its siblings

When a scoped child fails, the scope requests cancellation of surviving sibling work. That prevents a group of related operations from continuing indefinitely after the group can no longer produce its intended result.

The children must still all be joined:

```terrane
namespace failing-task-cancels-sibling
from /core/errors import throwable, coercion-error

async function fail int throws throwable;
  throw coercion-error

async function survive int;
  return 7

async function main;
  scope = task-scope;
  failing = scope.spawn; fail
  sibling = scope.spawn; survive
  failed = await scope.join; failing
  survived = await scope.join; sibling
  print; failed.completed, failed.cancelled
  print; survived.cancelled
```

There is an intentional race here. `survive` may finish before cancellation reaches it, or cancellation may be observed first. Correct code should not depend on one fixed ordering unless the program itself establishes that ordering.

What remains deterministic at the language level is the ownership structure:

- both children belong to `scope`;
- the failure is retained in `failed`;
- sibling cancellation is requested;
- both child values are consumed by joins;
- no child silently outlives the scope.

## Cancellation and partial progress

Cancellation is a request for cooperative termination, not a rewind operation.

A scope can request cancellation explicitly:

```terrane
scope.cancel;
```

For example:

```terrane
namespace cancelled-task-progress

async function work int;
  return 7

async function main;
  scope = task-scope;
  child = scope.spawn; work
  scope.cancel;
  outcome = await scope.join; child
  consistent = (outcome.cancelled and outcome.value == none) or (outcome.completed and outcome.value != none)
  print; consistent
```

This program prints:

```text
true
```

It does not assert that the child must be cancelled. The child is small and may complete before it observes the cancellation request. Either of these outcomes is coherent:

- cancellation is observed before successful completion, so no value is available;
- the child completes and retains its value.

A completed outcome may also record that cancellation was requested. `completed` and `cancelled` answer different questions: whether the child succeeded, and whether cancellation participated in its execution. Do not treat them as simple opposites.

This distinction matters for useful work. Suppose several tasks process independent records and cancellation arrives after some have completed. Their completed results do not become unreal. The supervising code can observe partial progress through the outcomes it joins.

### Cancellation points

A task observes cancellation at defined points rather than at an arbitrary instruction in the middle of an operation. `await`, scope joins, and operations explicitly documented as cancellable provide such points.

This makes cleanup and invariants tractable. Code is not interrupted between any two machine instructions merely because cancellation was requested.

It also means that cancellation is cooperative. A task must eventually reach a cancellation point for the request to affect its progress. A long computation with no suspension or cancellable operation should not be assumed to stop immediately.

### Cancellation while an operation is suspended

When a task observes cancellation while waiting inside a dependency or compiler-owned operation,
the executor stops polling and drops that in-flight operation. Rust resources owned only by the
operation run their `Drop` implementations promptly.

Terrane cleanup is stronger than simply dropping the whole task. Active `finally` blocks remain
owned by compiler-generated cleanup state. They run exactly once, from the innermost active block
outward, before the task's join can finish. A cleanup block may itself use `await`; it is shielded
from the cancellation request that caused cleanup to begin so that the same request cannot skip or
restart it.

This affects how values may cross a suspension point. A value needed both by the pending operation
and by later cleanup must have an ownership arrangement the compiler can separate safely. Overlapping
exclusive ownership, or a borrowed value whose owner cannot be proven alive through cleanup, is
rejected rather than being left to executor timing.

A deadline follows the same rule. It requests cancellation and drops the pending operation, but it
does not hard-kill `finally`. If cleanup waits on an external operation that never wakes, joining the
task can still remain pending. Keep cancellation cleanup bounded when progress depends on an
external system.

### Cancellation does not replace joining

This is incomplete:

```terrane
scope = task-scope;
child = scope.spawn; work
scope.cancel;
```

Cancellation requests that the work stop. It does not consume `child`, observe its final state, or prove that the child has finished. The program must still join it:

```terrane
scope.cancel;
outcome = await scope.join; child
```

That rule closes a common hole in concurrent programs: cancellation cannot be used as a synonym for forgetting.

## Deadlines

A task scope may carry a deadline budget:

```terrane
parent = task-scope; 10
```

A child scope can request a shorter budget:

```terrane
child = parent.child-scope; 5
```

Nested scopes may shorten their parent's deadline, but they may not extend it. This preserves a useful guarantee: once an operation has been given a maximum lifetime, deeper code cannot silently claim more time.

A statically visible extension is rejected:

```terrane
parent = task-scope; 5
child = parent.child-scope; 10
```

When the relationship depends on runtime values, the effective child deadline is clamped to the earlier of the parent deadline and the requested child deadline.

The current hosted runtime profile interprets integer deadline budgets as milliseconds. Treat that unit as a profile-level facility rather than building a general theory of time from an integer literal. Later standard time facilities can provide richer deadline values without changing the structural rule: a child may shorten a deadline, never extend it.

Deadlines use the same cooperative machinery as cancellation. Reaching the deadline requests cancellation; the scope still joins its children and preserves observable partial progress.

## Sharing mutable state by giving it one owner

Concurrent tasks often need to coordinate around changing application state. Terrane version one
does not put an arbitrary value behind a generic shared mutex. Instead, one task owns and mutates
the state while other tasks exchange typed commands and results with it through bounded channels.

```terrane
command-pair = channel; string, 4, channel-block
result-pair = channel; int, 1, channel-block
scope = task-scope;
owner = scope.spawn; (own-state; command-pair.receiver, result-pair.sender)
client = scope.spawn; (use-state; command-pair.sender, result-pair.receiver)
owner-outcome = await scope.join; owner
client-outcome = await scope.join; client
```

Here `own-state` receives commands and is the only function that mutates the state object.
`use-state` transfers commands through one channel and receives snapshots or operation results
through the other. The channel capacities make backpressure explicit, endpoint ownership makes
shutdown visible, and the task scope still accounts for both participants.

This is a design boundary, not a missing spelling. Importing `mutex`, `read-write-lock`, or
`shared-cell` and trying to construct a generic cell produces a diagnostic directing you back to
the owner-task pattern. The integer-specific synchronization objects remain available for
low-level counters and coordination, but they do not generalize to arbitrary application values.

Choose the owner-task shape when several concurrent activities need one logical writer. It keeps
the mutation in one sequential place, which is usually easier to reason about than a critical
section that might accidentally suspend while holding shared state.

## Threaded and cooperative executor profiles

Terrane source describes tasks, scopes, joins, cancellation, and deadlines. It does not hard-code one executor into those constructs.

The default hosted package profile uses the threaded executor. A package can select the cooperative executor in `package.toml`:

```toml
package = "cooperative-task-scope"
executor = "cooperative"

[namespaces]
cooperative-task-scope = "app"
```

The Terrane source does not change:

```terrane
namespace cooperative-task-scope

async function work int;
  return 9

async function main;
  scope = task-scope;
  child = scope.spawn; work
  outcome = await scope.join; child
  value = outcome.value
  if value != none
    print; outcome.completed, outcome.cancelled, value
```

It prints:

```text
truefalse9
```

The profile selects how the runtime drives the tasks. It does not change the source contracts:

- async invocation still produces a linear task;
- `await` still consumes a direct task;
- spawned children still belong to their scope;
- every child must still be joined;
- cancellation remains cooperative;
- outcomes retain completion, cancellation, value, and error information.

Application code should therefore choose an executor profile for deployment needs, not encode executor-specific timing assumptions into program logic.

## Project: processing several values concurrently

We can now combine the chapter's pieces in a small supervisor. The individual functions are intentionally simple; the point is the shape of the coordination.

```terrane
namespace concurrent-values

async function first-value int;
  return 3

async function second-value int;
  return 5

async function third-value int;
  return 8

async function main;
  scope = task-scope;

  first = scope.spawn; first-value
  second = scope.spawn; second-value
  third = scope.spawn; third-value

  first-outcome = await scope.join; first
  second-outcome = await scope.join; second
  third-outcome = await scope.join; third

  first-result = first-outcome.value
  second-result = second-outcome.value
  third-result = third-outcome.value

  if first-result != none
    print; 'first: ', first-result

  if second-result != none
    print; 'second: ', second-result

  if third-result != none
    print; 'third: ', third-result
```

The output is observed in join order:

```text
first: 3
second: 5
third: 8
```

The functions may make progress independently, but `main` presents their outcomes deterministically. Concurrency does not require nondeterministic output.

The program has one weakness: it prints whichever values are present without explaining absent ones. A fuller application would inspect each complete outcome, distinguishing successful completion, failure, and cancellation according to its own policy. The task scope provides the facts; the application decides what those facts mean to its users.

The structure scales more importantly than the toy calculation:

1. Create one owner for a related group of tasks.
2. Spawn the independent work before joining it.
3. Retain every child handle.
4. Join every child exactly once.
5. Inspect outcomes rather than assuming success.
6. Present results in an order chosen by the application.

That is the reusable part of the example.

## Terrane style: keep concurrency within a scope

When concurrency is needed, make its lifetime visible in the program's structure.

Prefer:

```terrane
scope = task-scope;
first = scope.spawn; first-work
second = scope.spawn; second-work
first-outcome = await scope.join; first
second-outcome = await scope.join; second
```

The code identifies the owner, the children, and the points where their outcomes are observed.

Do not look for a way to start work and discard its handle. Terrane intentionally provides no implicit detach path for scoped tasks. Work that truly belongs to a longer-lived service needs a longer-lived structural owner, not a hole in the current scope.

Likewise, do not introduce tasks merely to make a sequential calculation appear sophisticated. This is clearer:

```terrane
value = calculate;
print; value
```

than creating a scope, spawning one calculation, and joining it immediately when no other work can progress.

Use asynchronous structure when the problem has asynchronous structure.

## Why Terrane: async is structured

Unstructured concurrency lets a child task escape the code that created it. Sometimes that feels convenient. The cost appears later:

- failures have no obvious observer;
- cancellation becomes a convention;
- captured values acquire surprising lifetimes;
- shutdown must discover work it did not retain;
- tests depend on timing because completion is no longer structurally awaited.

Terrane chooses a stricter default.

A direct asynchronous invocation produces a linear task that must be consumed. A scoped invocation produces a child that belongs to its task scope and must be joined. Failure requests cancellation of surviving siblings, but does not erase them. Cancellation requests termination, but does not replace observation. Deadlines propagate inward and cannot be extended by nested code.

Those rules turn concurrency from ambient activity into a value-and-scope relationship the compiler can check.

The ceremony is small:

```terrane
scope = task-scope;
child = scope.spawn; work
outcome = await scope.join; child
```

What it buys is substantial: when the scope's work is complete, the program has accounted for the task, its ownership, and its outcome.

## Exercises

1. Write an `async function` that returns a string. Invoke it from another asynchronous function, retain the task in a binding, and consume it with `await`.
2. Remove the `await` from the first exercise while leaving the task in scope. Read the compiler's linear-task diagnostic, then restore the consuming operation.
3. Spawn two independent zero-argument asynchronous functions in one task scope. Join them in the opposite order from the order in which they were spawned, and present their values deterministically.
4. Change one child in the previous exercise so that it throws. Inspect the failed child's `completed`, `cancelled`, `value`, and `error` observations, and still join the surviving sibling.
5. Request cancellation after spawning a child. Write the outcome check so that both successful completion before cancellation and observed cancellation are valid.
6. Give a parent scope a deadline, then create child scopes with shorter and longer requested budgets. Confirm which requests are accepted by the nesting rule.
7. Run the same deterministic task program with the threaded and cooperative executor profiles. Compare its output, then explain which timing assumptions the source deliberately avoids.
8. Choose one sequential operation from an earlier chapter. Decide whether anything else could make meaningful progress while it waits; keep it sequential unless the answer is genuinely yes.

## Chapter summary

- Declare asynchronous work with `async function`.
- Invoking an asynchronous function produces a linear task.
- `await` consumes a direct task and is valid in asynchronous functions.
- A task that is not consumed is a source error.
- `task-scope;` creates a structural owner for concurrent child work.
- `scope.spawn; work` passes a zero-argument asynchronous callable to the scope.
- `await scope.join; child` transfers and consumes the child automatically and returns its outcome.
- Outcomes expose `completed`, `cancelled`, `value`, and `error`.
- Every spawned child must be joined, including after cancellation or sibling failure.
- Cancellation is cooperative and may race successful completion.
- A completed value remains meaningful even if cancellation was requested.
- Child scopes may shorten a parent's deadline but never extend it.
- Executor profiles may change how tasks are driven without changing Terrane's source semantics.
- Prefer ordinary sequential code when the problem is sequential; when concurrency is real, keep it inside an explicit scope.
