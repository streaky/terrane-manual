# 9. Classes, Interfaces, and Traits

The programs we have built so far have mostly kept data in ordinary values and collections, with functions performing the work. That remains a good default. A class should not be the admission price for writing a useful Terrane program.

Chapter 7 briefly used a class implementing `throwable` to define a structured domain error. We treated that declaration as one complete pattern before we had the vocabulary to examine it. Now we will make the object model explicit: what a class promises, how an instance is constructed, and why interfaces and traits are separate tools rather than interchangeable varieties of inheritance.

Some parts of a program do become clearer when state and the operations that preserve its rules have one home. A task has a title and a completion state. Completing it should be an operation on that task, not a convention repeated by every caller. Several kinds of task may need to appear through one common view. A small piece of behavior may also be useful to several otherwise unrelated classes.

Terrane provides four related ideas for those jobs:

- a **class** groups stored state with behavior and may extend one base class;
- an **interface** names a behavior contract that can be used as a type;
- a **trait** reuses fields and method implementations without becoming a type;
- a **protocol** describes a structural capability understood by the language or a library.

This chapter concentrates on the first three. Protocols usually appear through ordinary operations: an object can be iterable, displayable, comparable, or callable because it supplies the corresponding behavior. You do not normally begin a design by drawing a protocol hierarchy.

In this chapter, we will:

- define and construct classes;
- give instances typed fields and methods;
- initialize and clean up values through lifecycle methods;
- control which members callers may use;
- extend one concrete class;
- use an interface as a shared behavior boundary;
- reuse an implementation with a trait;
- build a small task-list model from those pieces.

The aim is not to turn every record of data into an object. It is to learn what each object-model tool says and to use one only when it makes the program more honest.

## Objects as behavior

Terrane says that everything is an object semantically. An integer, a string, a function, a class, and an instance all participate in one language model: they have types, may expose members, and may support protocols.

That does not mean everything is an instance of a user-defined class. Nor does it mean every value is a heap allocation carrying a table of methods. The statement is about what the program may observe, not about the compiler's eventual storage choice.

For this chapter, the useful consequence is simple:

> Think first about what a value can do. Choose a class when stored state and the operations that govern it belong together.

Suppose a program represents work with two unrelated values:

```terrane
title = 'Draft chapter'
completed = false
```

That is perfectly adequate while the program only stores and prints them. As the program grows, every function that changes a task must keep the two values together and preserve the same rules. A class lets us give that idea a name:

```terrane
class task
  title string
  completed bool
```

A `task` now describes objects with two fields. More importantly, it gives us a place to put operations such as `mark-complete` and `render`.

This is not automatically a better design merely because it uses a class. It becomes useful when the class owns a meaningful rule: for example, how a task is initialized, how its state changes, or how callers are allowed to observe it.

## Defining a class

A class declaration begins with `class` and a name. Its body is indented:

```terrane
class task
  title string
  completed bool
```

The declaration creates a class object named `task`. The indented declarations create its members.

Here, both members are instance fields. Each constructed task receives independent field state.
Because their declared types have canonical defaults:

- `title` stores a `string` and initially contains `''`;
- `completed` stores a `bool` and initially contains `false`.

A typed class field may omit a redundant initializer when its type has a canonical default:

```terrane
class counter
  value int
```

`bool` defaults to `false`; numeric fields receive typed zero; `string` and `bytes` receive empty
values; optional fields receive `none`; and collection fields receive empty collections. This
shorthand never guesses the field's type or puts hidden `none` into a non-optional field.

Write an initializer when the field needs a different default:

```terrane
class connection-options
  port uint16 = 443
  secure bool = true
```

A field whose type has no canonical default, such as another source-declared class, still requires
an initializer. The compiler therefore never leaves a constructed instance with unspecified bits.

A class may have an empty body when its name alone is useful:

```terrane
class marker
```

That is valid Terrane, although a class with neither meaningful state nor behavior should prompt the question of whether a simpler value would do.

## Constructing an instance

Terrane makes construction visible. Use `instance` followed by the class and a call marker:

```terrane
first task = instance task;
second task = instance task;
```

The semicolon belongs to the construction operation, just as it belongs to an ordinary call. It is required even when there are no arguments.

Construction is not written as a call to the class name:

```terrane
instance task;              # construct a task
task;                       # not construction
```

This distinction matters because a class is itself an object. Referring to or invoking a class object is not silently reinterpreted as creating an instance.

The word `instance` means *make a fresh semantic instance*. It does not promise heap allocation. The compiler may represent a particular instance as a Rust struct, a stack value, an enum alternative, or something more specialized. Source code receives the same class behavior whichever representation is chosen.

Every construction starts with independent instance state:

```terrane
first task = instance task;
second task = instance task;
first.completed = true
```

Changing `first.completed` does not change `second.completed`.

## Typed fields and ordinary methods

Methods are function declarations inside a class. Instance methods receive an implicit name, `this`, for the current instance:

```terrane
class task
  title string = ''
  completed bool = false

  function mark-complete;
    this.completed = true

  function render string;
    if this.completed
      return '[done] '.concat; this.title
    return '[ ] '.concat; this.title
```

The method header follows the same shape as a function header. A result type follows the method name:

```terrane
function render string;
```

Parameters follow the semicolon:

```terrane
function rename; title string
```

Inside an instance method, fields are selected through `this`:

```terrane
this.completed = true
return this.title
```

Outside the class, select an instance member with `.`:

```terrane
chapter = instance task;
chapter.title = 'Draft chapter'
chapter.mark-complete;
print; (chapter.render;)
```

The call marker is still explicit. `chapter.render` selects the method object; `chapter.render;` invokes it. Parentheses around the call delimit it before passing its result to `print`.

Methods may read fields, update them, call other methods, and return ordinary values. Terrane infers whether a method mutates its receiver from the method body. You do not add a `mutating` qualifier to repeat that fact.

### Fields express invariants

A field type is more than storage documentation. It is a contract for every value written to that field:

```terrane
class task
  title string = ''
  completed bool = false
```

No method or caller can replace `completed` with `'yes'`. The compiler checks assignments against the declared `bool` field.

Chapter 10 develops type annotations more fully. For now, typed fields give a class a stable shape and make its basic invariant visible where the state is declared.

### Field metadata

A field sometimes needs policy that is neither its Terrane name nor its type. An external document
may spell the key differently, or a value may be safe to hold but unsafe to expose in logs. Put
those facts on the field's one metadata clause:

```terrane
class service-options
  internal-name string = 'primary' metadata (external-name = 'serviceName')
  credential string = '' metadata (secret = true)
```

The clause follows the initializer. `external-name` takes a string and records the key used at a
document boundary. `secret` takes a boolean and marks the field for redaction before a structured
event reaches any sink. Metadata applies only to instance fields; repeating a metadata name or
giving two fields the same external name is rejected.

Defaults and optionality do not have separate metadata spellings. A canonical type default or an
ordinary initializer is the field default:

```terrane
retry-limit int = 3
```

An optional field continues to say so in its type:

```terrane
note string|none = none
```

Keeping those facts in the declarations that already define them prevents document decoding,
reflection, and logging from developing three subtly different descriptions of one class.

A class descriptor exposes the resolved field inventory:

```terrane
descriptor = service-options
print; descriptor.field-names[0]
print; descriptor.field-external-names[0]
print; descriptor.field-secret[1]
```

The reflected lists are parallel and declaration ordered. They retain the Terrane field name and
external name separately, and also expose whether each field is defaulted, optional, or secret.
They describe semantic fields rather than generated Rust identifiers.

### Decoding documents into classes

Field metadata also gives the compiler enough information to build an ordinary class value from
safe JSON or YAML. This is always explicit. Mark each class in the decoded tree with
`document-decodable`, then pass the concrete root descriptor and an unknown-field policy:

```terrane
from /core/documents import document-decodable
from /core/documents/json import decode-typed-json, default-json-options

class endpoint implements document-decodable
  host string = ''
  port uint16 = 443

class service-options implements document-decodable
  service-name string = '' metadata (external-name = 'serviceName')
  endpoint endpoint = instance endpoint;

decoded = decode-typed-json; source, service-options, (default-json-options;), false
if decoded.failed
  for diagnostic in decoded.diagnostics
    print; diagnostic.path, ': ', diagnostic.message
else
  print; decoded.value.endpoint.host
```

The decoder walks scalars, nested opted-in classes, lists, homogeneous tuples, and string-keyed
maps. It uses ordinary field initializers for absent defaults and accepts an absent `T|none`
field. Every other missing field is a diagnostic. Integer destinations are range checked.
Document numbers entering `float32` or `float64` use the same round-to-nearest, ties-to-even rule
as ordinary floating destinations; a magnitude outside the destination's finite range diagnoses.

The final boolean is deliberate policy. `false` rejects keys the class does not declare. `true`
ignores them recursively. Parser options still apply first, so opting into typed conversion does
not bypass JSON depth and byte bounds or YAML alias limits.

A failed outcome retains a safe ordinarily initialized value for a uniform result shape, but that
value is not partial success. Inspect `failed` and the typed `diagnostics` list. Each diagnostic
records the document path, expected type, actual kind, reason, message, the decode call location,
and the source declaration of the affected field. Errors in independent fields accumulate in
deterministic order.

Custom construction and resource-owning or inherited classes do not receive derived decoding.
Implement `deserializable` manually when construction itself owns policy. For a derived class that
only needs a final invariant check, also implement `document-validatable`:

```terrane
from /core/documents import document-validatable

function validate-document string|none;
  if this.service-name == 'reserved'
    return 'service name is reserved'
  return none
```

The method runs only after every field decoded successfully. A returned string becomes a
validation diagnostic; `none` accepts the value. Validation never receives a partially decoded
instance.

### Logging object-shaped values

Structured logging is one place where field metadata and interface behavior meet. Import
`/core/logging`, choose a sink explicitly, and enrich an immutable logger with typed fields:

```terrane
from /core/collections import list
from /core/logging import log-field, log-text, field, secret-field, memory-sink, default-logger, with-field, info

sink-result = memory-sink; 32, 'reject', 0, 1, false
log = default-logger; sink-result.value
log = with-field; log, (field; 'component', (log-text; 'importer'))

fields list of log-field = list;
fields.append; (secret-field; 'credential', (log-text; 'not-for-output'))
outcome = info; log, 'starting import', fields
```

There is no ambient application logger in this model. The logger names its sink and carries its
context as an ordinary value. `with-field` and `with-span` return enriched copies, so adding context
for one operation does not contaminate an earlier logger or a sibling copy.

Each field stores a `log-value` renderer rather than flattening the value immediately. Severity and
hierarchical target filters run before that renderer. A secret field is not rendered at all unless
the selected sink was explicitly created with permission to reveal secrets; otherwise the sink
receives the structured string `"<redacted>"`. The compiler preserves the call sites of field
construction and event emission so captured records can lead back to the source that supplied them.

Class metadata connects to the same policy. A descriptor-driven adapter checks `field-secret` and
uses `secret-field` for every matching class field. Logging does not invent a second secrecy
annotation, and generated Rust field names never participate in the decision.

Libraries reached through projected Rust dependencies may already emit through the Rust `log` or
`tracing` facades. `install-dependency-bridge; log` connects those process-global callbacks to this
logger's explicit sink. Install it deliberately near program startup. Foreign events keep their
dependency target, module, file, and line and identify their origin as `dependency`; they are not
given a convenient but false Terrane call site.

### Stored fields and computed members

An object may expose members that are not stored fields. For example, a string provides `length`,
but callers do not own a hidden integer slot that they may overwrite:

```terrane
title string = 'Draft chapter'
title.length = 40                 # rejected: `length` is read-only
```

The compiler reports `T0072` at `length`. The same rule applies to other computed or
compiler-owned members: selecting a value does not imply that the selection is an assignment
target.

Source-declared fields remain writable when their visibility and type permit it:

```terrane
chapter = instance task;
chapter.title = 'Review examples'
chapter.completed = true
```

This distinction keeps object surfaces honest. Assignment updates declared state; it cannot replace
facts such as a string's length, a floating value's finiteness, or a caught error's message
envelope. Use the operation that changes the underlying value instead.

## Initialization with `construct`

Default field values make zero-argument construction safe, but callers often need to supply initial state. `construct` is the conventional lifecycle method invoked by `instance`:

```terrane
class task
  title string = ''
  completed bool = false

  function construct; title string
    this.title = title
```

Construction can now pass the title:

```terrane
chapter task = instance task; 'Draft chapter'
```

The operation proceeds conceptually in two parts:

1. a fresh task begins with definitely initialized fields;
2. its `construct` method receives the supplied arguments and establishes the requested state.

`construct` is an ordinary instance method with a conventional role. Its parameters use the same rules as other function parameters, including defaults:

```terrane
class task
  title string = ''
  category string = 'general'

  function construct; title string, category string = 'general'
    this.title = title
    this.category = category
```

Both forms are then valid:

```terrane
first = instance task; 'Draft chapter'
second = instance task; 'Review examples', 'book'
```

The class name after `instance` is a class designator, not a return type and not an argument. The explicit spelling makes new semantic identity easy to see at the call site.

### Terrane style: construct a valid value

Prefer constructors that leave the instance ready to use. Avoid a sequence in which callers must construct an empty object and then remember several unrelated assignments:

```terrane
item = instance task;
item.title = 'Draft chapter'
item.category = 'book'
```

When those values are required to make a meaningful task, put the rule in `construct`:

```terrane
item = instance task; 'Draft chapter', 'book'
```

A short constructor is not merely convenient. It reduces the number of temporarily incomplete states that the rest of the program must understand.

## Cleanup with `destruct`

Some objects own work that must happen when their lifetime ends: closing a file, releasing a native handle, or committing a scoped resource. A class can declare a `destruct` method:

```terrane
class trace-scope
  name string = ''

  function construct; name string
    this.name = name
    print; 'enter ', this.name

  function destruct;
    print; 'leave ', this.name
```

`destruct` is a deterministic cleanup hook. Terrane invokes it once for each independently owned source value when that value's lifecycle ends. User code should not normally call it directly.

That wording matters because ordinary assignment has value semantics. If assigning an object creates an independent logical value, each independent value has its own lifecycle and therefore its own cleanup. A `move`, introduced in Chapter 11, transfers an existing lifecycle rather than creating another one.

When a subclass and its base both declare `destruct`, cleanup runs from the most-derived class toward the root base. Derived cleanup can still use inherited state, and base cleanup is not skipped merely because the method name was overridden.

Do not add `destruct` to ordinary data objects for ceremony. It represents observable cleanup and should exist only when the model genuinely requires it.

## Encapsulation and visibility

Members are public by default. This keeps small classes lightweight:

```terrane
class task
  title string = ''

  function render string;
    return this.title
```

When a class owns an invariant, visibility can keep callers on the operations that preserve it. Terrane provides three visibility levels inside a class:

- `public` is visible to all permitted callers;
- `protected` is visible to the class and its descendants;
- `private` is visible only to the declaring class.

Consider a task collection:

```terrane
class task-list
  private items list of task = list

  function add; item task
    this.items = this.items.append; item

  function count int;
    return this.items.length
```

Callers may add a task or ask for the count, but they cannot replace `items` directly. The class controls the operations through which its collection changes.

Writing `public` is allowed when it helps document an API, even though public is the default:

```terrane
public function count int;
```

Use visibility to protect a real boundary, not to make every declaration longer. A field does not become unsafe merely because it is public, and a getter that exposes exactly the same unrestricted mutation is not meaningful encapsulation.

### Terrane style: expose the rule, not the storage ritual

Suppose callers should complete a task through one operation. Prefer:

```terrane
item.mark-complete;
```

to spreading knowledge of its internal representation:

```terrane
item.completed = true
```

The first form gives future validation, timestamps, or reporting behavior one natural home. The class has earned some of its existence by naming a domain operation.

Not every field needs to be private. A title that callers are genuinely free to read and replace may remain public. Encapsulation should communicate a design decision, not imitate a style guide from a language with different defaults.

## Extending one base class

A class may extend one concrete base class:

```terrane
class urgent-task extends task
```

The subclass inherits the base class's fields and methods. It may add its own state and may replace inherited behavior:

```terrane
class task
  title string = ''
  completed bool = false

  function render string;
    if this.completed
      return '[done] '.concat; this.title
    return '[ ] '.concat; this.title

class urgent-task extends task
  function render string;
    if this.completed
      return '[done, urgent] '.concat; this.title
    return '[urgent] '.concat; this.title
```

An `urgent-task` can use the inherited `title` and `completed` fields. Calling its `render` method uses the subclass behavior.

Single inheritance represents an **is-a relationship with inherited state**. An urgent task is a task, and code expecting a `task` can receive one:

```terrane
urgent urgent-task = instance urgent-task;
ordinary-view task = urgent
```

That conversion preserves the complete dynamic object. It does not cut away the subclass portion merely because the binding is typed as `task`. If an overridden method is called through `ordinary-view`, the preserved concrete value still determines the behavior.

Terrane supports one base class rather than multiple class inheritance. When the need is shared behavior rather than one concrete is-a relationship, interfaces and traits usually state the design more precisely.

### Inheritance is not just code reuse

Do not introduce a base class solely because two classes happen to contain three similar lines today. Inheritance couples state, lifecycle, substitution, and method behavior.

A useful test is:

> Can every value of the proposed subclass honestly be used wherever the base class contract is expected?

If the answer is no, prefer an ordinary field, a helper function, or a trait for the reusable implementation. A hierarchy that exists only to avoid copying a small method is expensive documentation.

## Describing shared behavior with an interface

Sometimes callers do not care which concrete class they receive. They care that the value can perform a particular operation.

An interface names that behavior contract:

```terrane
interface task-view
  function render string;
```

A class declares that it implements the interface:

```terrane
class task implements task-view
  title string = ''

  function render string;
    return this.title
```

The compiler checks the complete required signature. A class that omits `render`, returns the wrong type, or accepts incompatible parameters does not implement `task-view` merely because it says so.

Interfaces can be used in annotations:

```terrane
function show; item task-view
  print; (item.render;)
```

Both an ordinary task and an urgent task may cross that boundary:

```terrane
show; (instance task;)
show; (instance urgent-task;)
```

The function knows only the behavior promised by `task-view`. It cannot depend on unrelated fields that happen to exist on one implementation.

This is the central distinction:

- a class describes a concrete family of state and behavior;
- an interface describes the behavior a boundary requires.

An interface is a type. A trait, which we will meet next, is not.

### Interfaces preserve mutation contracts

An interface may include methods that mutate their receiver:

```terrane
interface completable
  function mark-complete;
  function is-complete bool;
```

A conforming implementation supplies bodies with compatible signatures and receiver behavior. Terrane infers receiver mutation from concrete bodies and retains that fact when checking interface calls. You do not decorate the interface with a general-purpose mutation keyword.

### Prefer the smallest useful interface

An interface should describe what its consumers need, not inventory an entire concrete class.

If a report renderer only needs this:

```terrane
interface task-view
  function render string;
```

then adding setters, storage fields, construction details, and administrative methods makes the boundary weaker rather than stronger. Small interfaces admit more honest implementations and make dependencies easier to understand.

## Reusing fields and methods with traits

A trait supplies reusable implementation to classes:

```terrane
trait categorized
  category string = 'general'

  function render-category string;
    return ' ('.concat; this.category, ')'
```

A class uses the trait with `uses`:

```terrane
class task uses categorized
  title string
```

The class receives the trait's `category` field and `render-category` method. Its own methods can use them through `this`:

```terrane
function render string;
  return this.title.concat; (this.render-category;)
```

Trait fields follow the same default rules as class fields. A defaultable field may omit its
initializer and contributes that canonical value to every using class. A nondefaultable field must
be initialized by the trait or overridden with an initializer in the using class; the compiler
validates the complete inherited field set before construction. An initializer inherited from a
trait or base class is still evaluated in the source and object context where it was declared.

A trait is implementation reuse, not a type relationship. This is invalid as a promise that a parameter accepts every class using `categorized`:

```terrane
function show-category; item categorized    # not a trait type boundary
```

If callers need a named type boundary, define an interface containing the required behavior. A trait may help classes implement that interface, but the two ideas remain distinct.

A class may combine the object-model clauses in one header:

```terrane
class urgent-task extends task implements task-view uses categorized
```

Read that from left to right:

- it extends the concrete state and behavior of `task`;
- it promises the `task-view` interface;
- it incorporates the implementation from `categorized`.

### Trait conflicts are explicit

Two traits may not silently replace one another's member merely because they are listed in a particular order. This is rejected:

```terrane
trait left-label
  function marker string;
    return 'left'

trait right-label
  function marker string;
    return 'right'

class ambiguous uses left-label, right-label    # rejected: member conflict
```

Terrane does not apply a “last one wins” rule. A reusable implementation should remain reviewable when traits are reordered, and a conflict should force the class author to settle the meaning deliberately.

### Interface or trait?

Ask what the declaration is for:

| Need | Use |
|---|---|
| Store state and define one concrete kind of value | class |
| Accept different classes through one named behavior contract | interface |
| Reuse fields or method bodies in several classes | trait |
| Extend the state and substitutable behavior of one concrete kind | class inheritance |

A trait can help satisfy an interface. A subclass can inherit interface conformance from its base. Neither fact collapses the distinctions in the table.

## Designing an object that earns its existence

Classes are useful, but they are not the default container for every handful of values. Before creating one, ask what responsibility becomes clearer.

A class probably earns its existence when at least one of these is true:

- several fields form one invariant that its methods preserve;
- lifecycle behavior belongs to the value;
- callers benefit from a stable operation rather than manipulating representation;
- more than one concrete implementation must satisfy a shared interface;
- the value is a real domain concept with behavior that changes alongside its state.

A class is probably unnecessary when it only hides an ordinary collection behind one-line forwarding methods, or when a small function and a tuple already state the idea clearly.

Compare these two designs for a list of titles.

The first creates a class but adds no policy:

```terrane
class titles
  values list of string = list

  function append; value string
    this.values = this.values.append; value
```

An ordinary `list of string` may be clearer.

The second owns a domain rule:

```terrane
class task
  private completed bool = false

  function mark-complete;
    this.completed = true

  function status string;
    if this.completed
      return 'done'
    return 'open'
```

Here the methods name meaningful operations and keep the representation decision local.

### Terrane style: begin with values, grow toward contracts

You do not need to predict a complete object hierarchy before writing the first version of a program. Begin with ordinary values and functions. Introduce a class when state and behavior want one home. Introduce an interface when a real boundary needs several implementations. Introduce a trait when repeated implementation has become visible.

That order avoids speculative architecture and tends to produce smaller contracts.

## Project: model a small task list

We will now assemble the chapter's ideas into one program. The model has three goals:

1. ordinary and urgent tasks should render differently;
2. the list should accept either kind without knowing its concrete class;
3. category behavior should be reusable without making category a base class.

Start with the namespace, the collection import, and the shared rendering interface:

```terrane
namespace task-list-project

from /core/collections import list

interface task-view
  function render string;
```

`task-view` is deliberately small. The task list needs to render each item; it does not need permission to rewrite every field.

Next, define a trait for the reusable category field and its formatting behavior:

```terrane
trait categorized
  category string = 'general'

  function render-category string;
    return ' ('.concat; this.category, ')'
```

Now define the main task class:

```terrane
class task implements task-view uses categorized
  title string = ''
  completed bool = false

  function construct; title string, category string = 'general'
    this.title = title
    this.category = category

  function mark-complete;
    this.completed = true

  function render string;
    if this.completed
      return '[done] '.concat; this.title, (this.render-category;)
    return '[ ] '.concat; this.title, (this.render-category;)
```

This class has one concrete representation, promises the `task-view` boundary, and reuses the `categorized` implementation. `construct` establishes a useful task in one operation. `mark-complete` names the state transition. `render` fulfills the interface.

An urgent task is still a task, but it changes how open work is presented:

```terrane
class urgent-task extends task
  function render string;
    if this.completed
      return '[done, urgent] '.concat; this.title, (this.render-category;)
    return '[urgent] '.concat; this.title, (this.render-category;)
```

The subclass inherits the fields, constructor, trait-provided method, and interface conformance of `task`. It overrides only the behavior that differs.

Finally, define the collection object:

```terrane
class task-list
  private items list of task-view = list

  function add; item task-view
    this.items = this.items.append; item

  function show;
    for item in this.items
      print; (item.render;)
```

The private list stores interface-typed values. `task-list` does not need an `if` that asks which class each item belongs to. It invokes the operation guaranteed by `task-view`, and dynamic behavior selects the appropriate implementation.

The assignment in `add` is intentional:

```terrane
this.items = this.items.append; item
```

It makes the containing field update visible to the compiler and keeps the changed list in `items`.

Here is `main`:

```terrane
function main;
  chapter = instance task; 'Draft chapter', 'writing'
  chapter.mark-complete;

  review = instance urgent-task; 'Review examples', 'book'

  tasks = instance task-list;
  tasks.add; chapter
  tasks.add; review
  tasks.show;
```

The complete program is:

```terrane
namespace task-list-project

from /core/collections import list

interface task-view
  function render string;

trait categorized
  category string = 'general'

  function render-category string;
    return ' ('.concat; this.category, ')'

class task implements task-view uses categorized
  title string = ''
  completed bool = false

  function construct; title string, category string = 'general'
    this.title = title
    this.category = category

  function mark-complete;
    this.completed = true

  function render string;
    if this.completed
      return '[done] '.concat; this.title, (this.render-category;)
    return '[ ] '.concat; this.title, (this.render-category;)

class urgent-task extends task
  function render string;
    if this.completed
      return '[done, urgent] '.concat; this.title, (this.render-category;)
    return '[urgent] '.concat; this.title, (this.render-category;)

class task-list
  private items list of task-view = list

  function add; item task-view
    this.items = this.items.append; item

  function show;
    for item in this.items
      print; (item.render;)

function main;
  chapter = instance task; 'Draft chapter', 'writing'
  chapter.mark-complete;

  review = instance urgent-task; 'Review examples', 'book'

  tasks = instance task-list;
  tasks.add; chapter
  tasks.add; review
  tasks.show;
```

Run it with:

```console
terrane run task-list.trn
```

It prints:

```text
[done] Draft chapter (writing)
[urgent] Review examples (book)
```

Notice what each mechanism contributes:

- `task` owns state and its state transition;
- `urgent-task` is a concrete specialization of `task`;
- `task-view` lets the collection accept both concrete classes;
- `categorized` reuses a field and formatting method;
- `task-list` hides collection storage behind the operations it wants to support.

Also notice what the program does not contain. There is no manual tag saying which concrete task is stored, no switch that selects a rendering function, and no universal boxed “object value” in the source. The object contracts carry exactly the distinctions the program needs.

### A value-semantics observation

The program completes `chapter` before adding it to the list:

```terrane
chapter.mark-complete;
tasks.add; chapter
```

That ordering avoids implying shared identity. Ordinary assignment and parameter passing preserve Terrane's value semantics. Adding `chapter` does not promise that later changes to the local binding will mutate the item already stored in `tasks`.

Most programs should begin with that independence. Chapter 11 introduces `ref` and `shared ref` for models in which two parts of a program intentionally observe one changing identity.

## Under the surface: the object model is a semantic abstraction

The source program says that `urgent-task` extends `task`, implements `task-view`, and receives behavior from `categorized`. Those are observable language contracts. They do not prescribe one matching family of Rust runtime objects.

The compiler might realize a closed group of classes as structs and an enum. It might turn an interface call into a direct call when the concrete class is known. It might use dynamic dispatch when the concrete alternatives must remain open. It might flatten inherited fields, specialize a method, or remove a descriptor that no runtime behavior can observe.

All of those choices are permitted if they preserve the Terrane program's behavior.

This is the companion to “everything is an object semantically”:

> No particular runtime object representation follows from that fact.

The relationship between Terrane's semantic object model and its runtime representation is intentionally not one-to-one. A member may cease to exist as a runtime lookup because the compiler has already proved which operation it means. An object may need no heap allocation. An interface may require no vtable in a program where every call target is statically known.

The programmer describes the behavior the program must appear to have. The compiler produces Rust that satisfies that description. Chapter 13 will inspect that generated Rust directly; for now, the important rule is not to design Terrane source around a guessed backend layout.

## Exercises

1. Add a `reopen` method to `task`. It should set `completed` back to `false`. Complete a task, print it, reopen it, and print it again.

2. Add a `rank int` field to `urgent-task`. Give it a default value and include it in a method that reports whether one urgent task should be considered before another. Keep the exercise focused on behavior; do not expose private collection storage merely to sort it.

3. Define a second class, `note`, that implements `task-view` without extending `task`. Give it one string field and a `render` implementation. Add both a `note` and a `task` to `task-list`. This tests whether the interface describes behavior rather than ancestry.

4. Move `completed` behind `private` visibility. Add an `is-complete bool` method and adjust `urgent-task` so that it can still implement its rendering behavior. What visibility would be required if a subclass must read the stored field directly?

5. Create a second trait that also declares `render-category`. Use it alongside `categorized` and read the compiler diagnostic. Then remove the conflict by deciding which single implementation the class should use; do not depend on trait order.

6. Add a `destruct` method to a small experimental class that prints its name. Construct two independent values in `main` and observe cleanup order. Then assign one value to another name and consider why independently owned values each have their own lifecycle. Keep `destruct` out of the task-list design unless cleanup is actually part of that domain.

## What we learned

A class gives related state and behavior one concrete home. `instance class; arguments` constructs a fresh semantic instance, and `construct` establishes its initial state. Instance methods use `this`; field types keep the object's shape valid; `destruct` expresses deterministic cleanup when a value genuinely owns such work.

Visibility protects meaningful invariants. Single inheritance extends one concrete class and preserves the complete dynamic value. An interface names behavior that different classes can promise at a typed boundary. A trait reuses implementation but is not itself a type.

The distinctions are most useful when kept sharp:

- use a class for a concrete stateful concept;
- use inheritance for an honest is-a relationship;
- use an interface for behavior required by a boundary;
- use a trait for shared implementation;
- use ordinary values and functions when none of those improves the design.

In the next chapter, we will make the type contracts used here more deliberate. We will begin with inference, add annotations where they communicate intent, and strengthen the task-list program without turning every obvious value into a declaration ceremony.
