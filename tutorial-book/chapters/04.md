# 4. Functions: Giving Work a Name

The number classifier at the end of Chapter 3 works, but all of its decisions live inside `main`. If another part of the program needs the same classification, we must either repeat the branches or give that work a name.

A function turns a piece of behavior into an object that can be called, passed, and composed. Its header states what information crosses the boundary. Its body keeps the implementation local.

In this chapter, we will:

- define and call functions;
- describe parameters and results;
- use required, optional, and named arguments;
- return as soon as a result is known;
- reason about local scope;
- pass a function as an ordinary value;
- assemble small functions into a larger operation;
- turn the number classifier into a reusable program.

Function boundaries are the first places where Terrane asks us to write types regularly. That is deliberate. Local values can remain inferred while the contract between two pieces of a program stays visible.

## Defining and calling a function

A function declaration begins with `function`, followed by its name and the call marker:

```terrane
function greet; name string
  print; 'Hello, ', name
```

The indented body belongs to the function. `name string` declares one parameter named `name` whose value must be a string.

Call the function with the same `;` used for every invocation:

```terrane
greet; 'Ada'
```

This prints:

```text
Hello, Ada
```

The declaration and call deliberately echo each other:

```terrane
function greet; name string
greet; 'Ada'
```

The semicolon in the declaration introduces the parameter list. The semicolon at the call site introduces the argument list. In both places, it marks the callable boundary rather than terminating a statement.

A function with no parameters still includes the marker:

```terrane
function announce;
  print; 'Ready'
```

Call it with:

```terrane
announce;
```

Leaving off the semicolon refers to the function object; it does not invoke it.

### Definitions do not run themselves

Declaring a function makes it available but does not execute its body:

```terrane
function announce;
  print; 'Ready'

function main;
  print; 'Before'
  announce;
  print; 'After'
```

The output is:

```text
Before
Ready
After
```

Execution enters `announce` only at the call and returns to the following statement when the function finishes.

### Unreferenced functions are reported

A top-level function that is never called, passed, or otherwise referred to does not prevent the
program from running. The compiler reports `W4005` at its source declaration instead:

```terrane
function leftover string;
  return 'not used'

function main;
  print; 'Ready'
```

This program prints `Ready` and also warns that `leftover` is never referenced. A warning is useful
here because the declaration may be an accidental remnant, but it may also be work deliberately
written ahead of its first caller. Remove the function when it is genuinely obsolete; otherwise the
program remains valid while you connect it.

## Parameters and results

Parameters carry values into a function. A result carries one value back.

Place the result type after the function name:

```terrane
function add int; left int, right int
  return left + right
```

Read the header as:

> `add` is a function that returns an `int` and accepts two `int` parameters, `left` and `right`.

Call it in an expression:

```terrane
total = add; 4, 7
print; total
```

The output is `11`.

A function returning a value must satisfy its result contract on every reachable path. This is rejected:

```terrane
function absolute int; value int
  if value < 0
    return -value
```

When `value` is nonnegative, execution could reach the end without producing the promised `int`. Complete the function:

```terrane
function absolute int; value int
  if value < 0
    return -value
  return value
```

A function without a result type performs work but produces no value:

```terrane
function show-total; total int
  print; 'Total: ', total
```

Do not invent a meaningless result merely so every function looks alike. A calculation should return its value; an operation whose contract is only an effect may have no result.

### Arguments are evaluated before the call

At a call site, each argument expression is evaluated and its value is passed to the corresponding parameter:

```terrane
result = add; 2 * 3, 4 + 1
```

`add` receives `6` and `5`, producing `11`.

A parameter is a local binding. Reassigning it changes the function's local parameter value; it does not create a hidden reference to the caller's binding:

```terrane
function increase int; value int
  value++
  return value

function main;
  original = 10
  changed = increase; original
  print; original, ', ', changed
```

The output is:

```text
10, 11
```

Terrane's ordinary value semantics remain in force across function calls. Chapter 11 introduces explicit references for functions whose contract genuinely includes shared identity.

## Required, optional, and named arguments

A parameter without a default is required:

```terrane
function report; name string, passed bool
```

Both arguments must be supplied:

```terrane
report; 'lexer', true
```

A default value makes a parameter optional:

```terrane
function report; name string, passed bool, attempts int = 1
  if passed
    print; name, ': passed in ', attempts, ' attempt(s)'
  else
    print; name, ': failed'
```

The caller may omit `attempts`:

```terrane
report; 'lexer', true
```

Inside the function, it receives the default value `1`.

Or the caller may provide it positionally:

```terrane
report; 'parser', true, 2
```

Required parameters must precede optional parameters in the declaration. Otherwise a positional call would have no stable way to say which value was omitted.

### Named arguments

A caller may bind an argument by parameter name:

```terrane
report; name = 'parser', passed = true, attempts = 2
```

Named arguments may appear in a different order:

```terrane
report; attempts = 2, name = 'parser', passed = true
```

Both calls mean the same thing. The names are part of the function's exposed calling contract.

Named arguments are especially useful when several adjacent values have the same type or when a call supplies one optional policy among many:

```terrane
connect; host = 'example.test', port = 443, timeout = 10
```

A positional argument may not follow a named one:

```terrane
report; name = 'parser', true       # rejected
```

Once a call begins naming destinations, every later argument must be named too. This prevents a reader from having to merge two ordering systems midway through the call.

### Defaults are evaluated by the declaration's contract

A default belongs to the parameter declaration:

```terrane
function report; name string, passed bool, attempts int = 1
```

The caller does not receive a special overloaded function with fewer parameters. It invokes the same callable while allowing the declared default to supply one argument.

Use defaults for values that are genuinely unsurprising. A default that changes safety, persistence, or destructive behavior deserves particular scrutiny; requiring the caller to state it may be clearer.

## Returning early

`return` immediately leaves the current function. When the function produces a result, the returned expression must satisfy its declared type.

Early returns are useful when a special case has a complete answer:

```terrane
function classify string; number int
  if number == 0
    return 'zero'

  if number < 0
    return 'negative'

  return 'positive'
```

Once zero is handled, later code does not need to nest inside `else`. Once a negative value returns, the final line necessarily handles a positive value.

Compare the nested form:

```terrane
function classify string; number int
  if number == 0
    return 'zero'
  else
    if number < 0
      return 'negative'
    else
      return 'positive'
```

Both can be correct, but the early-return version keeps the main path at one indentation level.

### Return when the answer is complete

An early return should express a completed decision, not scatter unexplained exits throughout a long body.

This is easy to follow:

```terrane
function admission string; age int
  if age < 0
    return 'invalid'
  if age < 18
    return 'minor'
  return 'adult'
```

Each branch settles the function's answer. If a function accumulates partial work that must be cleaned up or reported together, one carefully structured exit may be clearer. Chapter 7 adds error handling and deterministic cleanup to that decision.

A result-less function may return without a value:

```terrane
function show-if-positive; value int
  if value <= 0
    return
  print; value
```

The bare `return` ends the operation; it does not manufacture a `none` result.

## Local scope

Parameters and names first declared inside a function belong to that function:

```terrane
function area int; width int, height int
  result = width * height
  return result
```

The names `width`, `height`, and `result` are unavailable to unrelated functions.

This is rejected:

```terrane
function area int; width int, height int
  result = width * height
  return result

function main;
  print; result                 # unresolved here
```

Local scope lets a function choose implementation names without publishing them as part of its contract.

### Nested blocks have their own scope

Every indented control-flow body introduces a nested lexical scope:

```terrane
function describe string; value int
  if value < 0
    prefix = 'negative '
    return prefix.concat; (-value)

  return 'nonnegative'
```

`prefix` is available only inside the `if` body. It cannot be used after that body.

An existing outer binding remains visible and may be updated:

```terrane
function sum int; values list of int
  total = 0
  for value in values
    total = total + value
  return total
```

`total` is declared in the function body, so the loop updates that existing binding. The loop target `value` remains local to the loop body.

The `list` type used here comes from `/core/collections`; a complete source file would import its constructor and type vocabulary before this declaration.

### Keep local state local

If a value is used only to calculate one result, keep it inside the function that owns that calculation. Do not move it to namespace or global state merely so another function can reach it.

Prefer:

```terrane
function subtotal int; price int, quantity int
  return price * quantity
```

to a function that implicitly reads unrelated mutable program state. Explicit parameters make dependencies visible at the call site and make the function easier to reuse.

## Passing functions as values

A function name refers to a callable object. Without `;`, it can be assigned or passed like another value:

```terrane
function double int; value int
  return value * 2

operation function from int to int = double
```

The annotation:

```terrane
function from int to int
```

describes a callable accepting one `int` and returning one `int`.

Invoke the stored function normally:

```terrane
result = operation; 7
```

The result is `14`.

A function may accept another function as a parameter:

```terrane
function apply int; operation function from int to int, value int
  return operation; value
```

Call it by passing the function object rather than invoking it first:

```terrane
result = apply; double, 7
```

Inside `apply`, `operation; value` performs the invocation.

Compare the roles:

```terrane
double                 # the callable object
double; 7              # invoke it now
apply; double, 7        # pass it, then apply invokes it
```

The explicit call marker keeps these cases visually distinct.

### Callable contracts must match

A function value's parameter and result types are part of its type. A function accepting a string is not interchangeable with one accepting an integer merely because both are callable:

```terrane
function length int; text string
  return text.length

operation function from int to int = length     # rejected
```

Terrane checks this boundary before the call can occur.

Passing functions is useful when the caller owns the sequence of work but another part of the program should choose one operation: transforming a value, validating an item, formatting a result, or handling an event. Do not introduce a callback when one direct call is clearer.

## Small functions that compose

A useful function usually owns one recognizable decision or transformation. Small functions can then build larger behavior without duplicating that logic.

Begin with parity:

```terrane
function parity string; number int
  if number % 2 == 0
    return 'even'
  return 'odd'
```

Then use it inside a fuller classification:

```terrane
function classify string; number int, detailed bool = true
  if number == 0
    return 'zero'

  kind = parity; number
  if not detailed
    return kind
  if number < 0
    return 'negative '.concat; kind
  return 'positive '.concat; kind
```

`classify` does not reproduce the remainder calculation. It delegates that decision to `parity` and adds sign information when requested.

Composition is not a contest to produce the shortest possible functions. This extraction would add little:

```terrane
function zero int;
  return 0
```

A function earns its name when the name communicates an idea, the boundary enables reuse or testing, or the implementation contains a rule worth keeping in one place.

### Keep data movement visible

This composition remains straightforward:

```terrane
kind = parity; number
return 'positive '.concat; kind
```

A deeply nested chain of tiny calls can obscure the intermediate ideas it supposedly clarifies. Giving an important intermediate result a name is often better than minimizing line count.

Terrane's parenthesized nested calls remain available when a value is genuinely used once:

```terrane
print; 'Classification: ', (classify; number)
```

Use the form that makes the stages easiest to read.

## Project: turn the number classifier into functions

We will now refactor Chapter 3's classifier. The loop will supply numbers, while functions own the reusable decisions.

Create `number-classifier-functions.trn`:

```terrane
namespace number-classifier-functions

from /core/collections import range

function parity string; number int
  if number % 2 == 0
    return 'even'
  return 'odd'

function classify string; number int, detailed bool = true
  if number == 0
    return 'zero'

  kind = parity; number
  if not detailed
    return kind
  if number < 0
    return 'negative '.concat; kind
  return 'positive '.concat; kind

function double int; value int
  return value * 2

function apply int; operation function from int to int, value int
  return operation; value

function main;
  numbers = range; -3, 5
  for number in numbers
    print; number, ': ', (classify; number)

  print; 'brief: ', (classify; 4, false)
  print; 'named: ', (classify; detailed = false, number = -3)
  print; 'passed: ', (apply; double, 7)
```

Run it:

```console
terrane run number-classifier-functions.trn
```

It prints:

```text
-3: negative odd
-2: negative even
-1: negative odd
0: zero
1: positive odd
2: positive even
3: positive odd
4: positive even
brief: even
named: odd
passed: 14
```

The program exercises three calling styles:

```terrane
classify; number
classify; 4, false
classify; detailed = false, number = -3
```

The first uses the default `detailed = true`. The second supplies both arguments positionally. The third names both arguments and changes their order.

It also passes `double` to `apply`:

```terrane
apply; double, 7
```

No special callback syntax is involved. `double` is a value satisfying the declared callable contract, and `apply` invokes it.

Most importantly, `main` no longer contains the classification rules. It describes the program's orchestration: obtain numbers, classify each one, and print a few variations. `parity` and `classify` own the decisions.

## Terrane style: express contracts, not ceremony

Function headers are valuable because they describe boundaries:

```terrane
function classify string; number int, detailed bool = true
```

A reader can see what the function accepts, what it returns, and which policy is optional without reading its body.

Inside the function, obvious locals remain inferred:

```terrane
kind = parity; number
```

Writing another annotation there would usually repeat information the compiler and reader already have. Add a local annotation when it communicates an intended narrowing, a public format, a union boundary, or another fact inference would not express clearly—not merely to prove that the program has types.

The same principle applies to decomposition. A function should expose a meaningful operation, not wrap every expression in a ceremonial name. Prefer the smallest set of functions that makes rules, reuse, and data flow clear.

A good boundary answers useful questions:

- What must the caller provide?
- What result can the caller rely on?
- Which values have meaningful defaults?
- Can the operation be passed where this callable contract is expected?

The body answers a different question: how is that contract fulfilled here?

## What we learned

A function gives behavior a name and a typed boundary. Parameters carry values in; `return` carries a result out. Required parameters precede optional parameters, defaults supply omitted arguments, and named arguments make selected call-site intent explicit.

Parameters and local bindings belong to the function. Nested control-flow bodies introduce narrower scopes, while assignment can deliberately update a binding from an enclosing function body. Early returns keep completed special cases from forcing unnecessary nesting.

Functions are objects. A bare function name passes the callable; `;` invokes it. Callable types such as `function from int to int` let functions cross bindings and parameter boundaries with their contracts checked.

Small functions compose when each names a real decision or transformation. Their headers should express contracts, while inferred locals and direct expressions prevent those contracts from becoming ceremony.
