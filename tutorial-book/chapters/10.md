# 10. Types Without Ceremony

The task-list model already contains types. `task`, `urgent-task`, and `task-list` are concrete classes. `task-view` is a shared behavior boundary. Fields such as `title string` and `completed bool` state what each instance may contain. The compiler also inferred types for local names such as `chapter`, `review`, and `tasks`.

This chapter is not where an untyped language suddenly becomes typed. Terrane values have had types from the first string and integer in Chapter 1. We will instead learn when inference says enough, when an annotation improves a contract, and how unions, optional values, coercion, refinement, generic type constructors, and function types let larger programs remain precise.

The aim is captured by the chapter title: use types to express real guarantees without turning obvious local values into declaration ceremony.

## Type inference

Terrane can infer a binding's type from its initializer:

```terrane
name = 'Draft chapter'
completed = false
count = 3
```

The values are still typed:

- `name` receives a string value;
- `completed` receives a Boolean value;
- the unconstrained whole-number constant gives `count` the semantic `int` type.

Inference removes repetition where the initializer already answers the question. This is usually clear:

```terrane
tasks = instance task-list;
```

Writing the annotation can repeat useful information, but it does not make the constructed value more of a `task-list`:

```terrane
tasks task-list = instance task-list;
```

The annotation becomes more valuable at a boundary, where it states what callers may rely on rather than merely describing one current initializer:

```terrane
function add; item task-view
```

The caller may pass any value satisfying `task-view`; the implementation promises not to require some narrower concrete class. Inference from the first call would be the wrong contract because a later call may legitimately pass a different implementing class.

Numeric constants are context-sensitive before they become values. Here the destination chooses a fixed representation:

```terrane
priority int8 = 4
```

The compiler checks that the exact constant fits `int8` and materializes it directly. Without context, `4` ordinarily becomes `int`:

```terrane
priority = 4
```

Neither spelling is universally better. Use `int` when the quantity is semantically exact and unbounded by the program's contract. Use a fixed width when interoperability, layout, or a genuine domain bound makes that width meaningful.

## Annotations where they communicate intent

Annotations earn their place when they constrain a boundary, document an otherwise non-obvious alternative, or prevent an implementation detail from becoming the contract accidentally.

Function parameters and results are strong examples:

```terrane
function high-priority bool; priority int8
  return priority >= 8
```

The header says everything a caller needs to know about ordinary input and output. The body remains free to change without changing that promise.

Collection element types are also worth stating when the empty constructor provides no evidence:

```terrane
items list of task-view = list
```

Without the annotation, an empty `list` has no element from which to infer the intended boundary. `list of task-view` also communicates that the collection deliberately accepts different implementing classes rather than one concrete task class.

Optional state deserves an annotation because `none` alone does not identify what a present value would be:

```terrane
estimate int|none = none
```

By contrast, this local is already obvious:

```terrane
input-priority = 9
```

Adding `int` may still be useful when the distinction between arbitrary-precision `int` and a fixed integer is central to the nearby conversion. In the chapter project we will write it explicitly for that reason.

A practical rule is:

> Annotate the promise, the empty case, and the surprising choice. Infer the immediate and obvious.

That rule is guidance, not a syntactic restriction. Explicit annotations remain legal wherever a source contract benefits from them.

## Union types and optional values

A union says that a value may belong to any one of several named types:

```terrane
result int|string
```

The separator is `|`. Arm order does not define preference or runtime search order. The compiler normalizes the union by semantic type identity.

The most common small union adds absence:

```terrane
estimate int|none
```

`none` is a real singleton absence value, not an uninitialized memory state and not a spelling for every failure. A task estimate may be absent because estimating work is optional. That is ordinary information, so `none` is appropriate.

A method can expose the optional value directly:

```terrane
function estimate-units int|none;
  return this.estimate
```

Callers must account for both possibilities. This is rejected conceptually because addition requires an integer, not the union of an integer and absence:

```terrane
estimate int|none = item.estimate-units;
total = total + estimate             # estimate may be none
```

The type prevents an absent estimate from silently becoming zero. Zero is a real estimate; absence means no estimate was supplied.

Use a typed error rather than `none` when the caller needs a failure category, explanation, cause, or recovery distinction. Chapter 7's invalid report entry was not ordinary absence: the report contract had been violated and publication stopped.

Unions should name genuine alternatives, not become a storage drawer for unrelated values. If every consumer immediately asks which of six unrelated arms it received, a class or interface boundary may describe the domain more honestly.

## Refinement after a check

A direct check can refine an optional binding inside the guarded block:

```terrane
estimate int|none = item.estimate-units;
if estimate != none
  print; 'Estimate: ', estimate + 1
```

Before the `if`, `estimate` may be `int` or `none`. Inside the body reached only when it differs
from `none`, the compiler knows it is `int`. The addition and the call to `print` therefore receive
a concrete integer value.

Equivalent direct forms include checking `none != estimate` or negating an `is a none` membership
test. Refinement belongs to the named binding that was checked; it is not a global guess about
every expression that might produce the same value. Repeated member, index, and call expressions
are not narrowing subjects because another evaluation may produce a different value. Evaluate the
expression once, bind its result, then guard and use that stable name.

When an optional object contains the requested member, `T0031` includes this remedy rather than
merely claiming the member is absent: bind the optional-producing expression, guard the resulting
name with `!= none`, and select the member from that narrowed name.

Assignment invalidates the fact:

```terrane
if estimate != none
  estimate = none
  # estimate may no longer be used as int here
```

The compiler follows the current source path rather than trusting that a check performed earlier remains true after mutation.

Keep narrowing checks direct. Complicated combinations of `and` and `or` may express a valid Boolean decision without producing a simple reusable type fact. When later statements need the refinement, give the relevant check its own `if`.

Refinement is one reason to bind an intermediate rather than nesting every call:

```terrane
estimate int|none = item.estimate-units;
if estimate != none
  print; estimate + 1
```

The name gives both reader and compiler one stable subject whose type becomes more precise.

## Coercion

A type annotation does not mean “convert whatever is nearby somehow.” Terrane distinguishes contextual numeric destination conversion from a written conversion policy, and it rejects undeclared conversions rather than guessing.

Suppose an external setting arrives as `int`, while task priority is deliberately stored as `int8`:

```terrane
input-priority int = 9
urgent-priority int8 = input-priority.coerce; int8
```

The member family `coerce` belongs to the source value. The destination descriptor follows the call marker. The throwing default either produces an `int8` or throws `integer-conversion-overflow` when the value is outside the destination range.

When failure is an expected question, choose the checked child:

```terrane
unchecked-priority int = 300
checked-priority int8|none = unchecked-priority.coerce.checked; int8
if checked-priority == none
  print; 'Priority rejected: ', unchecked-priority
```

`checked` returns absence instead of throwing. It does not substitute zero, clamp to 127, or wrap to another number. Those would be different conversion policies with different names and availability.

Written integer-to-floating coercion deliberately permits IEEE rounding:

```terrane
completed int = 7
average float64 = completed.coerce; float64
```

That is different from placing an integer directly into a floating destination, which remains
exact-or-throw. Writing `coerce` says an approximate floating representation is acceptable.
Integers too large for any finite destination float raise `coercion-error`; the corresponding
`coerce.checked` form returns `none`.

Floating-width coercion follows the same throwing-versus-checked choice for finite overflow.
Infinity remains infinity with its sign, and NaN remains NaN; they are floating categories rather
than finite values that overflowed. Conversion in the other direction still requires an explicit
rounding operation.

Written coercion is not universal casting permission. A source and destination pair must declare the operation. In particular, converting a fractional floating value to an integer requires a rounding decision:

```terrane
rounded = ratio.round;
count int = rounded
```

A vague `ratio.coerce; int` is not available because it would hide whether the programmer intended round, floor, ceiling, or truncation.

When no built-in pair expresses the domain conversion, pass one typed converter explicitly:

```terrane
function priority-label string; value int
  if value > 7
    return 'urgent'
  return 'normal'

label = input-priority.coerce; string, priority-label
```

This is not a global cast declaration. The converter belongs to this call, must be a synchronous
`function from int to string`, and runs exactly once after the source is evaluated once. A
converter with the wrong parameter or result type is rejected. If it declares a throwable, that
failure travels through the call normally and must be handled wherever the surrounding function's
effect contract requires it. Policy children such as `coerce.checked` remain reserved for
compiler-declared conversion pairs and do not accept a converter.

Contextual numeric destinations preserve exact values or fail; a written operation selects a declared policy such as throwing or checked arrival. The important habit is to choose conversion because it expresses intended semantics, not because a type checker needs to be silenced.

## Generic types

Collections need to describe the values they contain. Terrane writes a type constructor followed by `of` arguments:

```terrane
list of task-view
map of string, int
```

These are parameterized, or generic, types. `list` supplies the collection behavior; `task-view` fixes the element contract for this use. Two instantiations have distinct types:

```terrane
names list of string = list
priorities list of int8 = list
```

An element accepted by one need not be accepted by the other.

Nested constructors remain explicit:

```terrane
boards map of string, list of task-view
```

Read from the outside inward: a map whose keys are strings and whose values are lists of task views.

Version one does not support source-declared type parameters. You cannot yet define a reusable source function such as an invented `function first of T`. Use concrete types, unions, interfaces, or generated concrete declarations. This is a deliberate boundary, not an invitation to simulate generics with an erased universal value.

Existing generic constructs remain powerful because the compiler knows their complete type arguments. It can reject appending a string to `list of task-view`, check every operation against the element contract, and lower concrete representations without universal boxing.

Type-constructor punctuation can become dense in a parameter list. Prefer one clear parameter per line for complicated signatures, and give important intermediate types names through domain interfaces or classes rather than nesting constructors merely to prove that the grammar allows it.

## Function types

Functions are values when a boundary needs behavior supplied by a caller. Their type names parameter types and a result:

```terrane
function from int8 to bool
```

A predicate with that type accepts one `int8` and returns `bool`:

```terrane
function high-priority bool; priority int8
  return priority >= 8
```

A method can receive the behavior:

```terrane
function show-matching; predicate function from int8 to bool
  for item in this.items
    priority int8 = item.priority-value;
    if predicate; priority
      print; (item.render;)
```

The caller passes the function value without invoking it:

```terrane
tasks.show-matching; high-priority
```

Inside `show-matching`, the semicolon invokes `predicate` with `priority`. The type guarantees that the supplied callable accepts the right input and returns a value usable as a condition.

For more than one parameter, list inputs before `to`:

```terrane
function from int, int to bool
```

Function types associate to the right, allowing functions that return functions to remain unambiguous. Most everyday callbacks should still have small contracts and descriptive names. A callable type does not make an opaque tangle of higher-order behavior easier to understand automatically.

Errors are part of callable compatibility too. A function that may escape an incompatible throwable cannot be passed where the consumer promises a narrower error boundary. Fewer compatible failures are acceptable; an unexpected new failure is not.

## Compile-time guarantees

The types in this chapter eliminate several plausible defects before execution:

- `list of task-view` rejects values without the required rendering, estimate, and priority behavior;
- `estimate int|none` prevents absence from being used as an integer before refinement;
- `priority int8` rejects constants outside its fixed range and checks runtime arrival;
- `function from int8 to bool` rejects callbacks with incompatible inputs or results;
- declared field and method result types prevent an implementation from silently changing a public contract;
- an unavailable coercion policy is rejected instead of guessed.

These guarantees are local and compositional. The compiler does not need to understand what “urgent” means to prove that `high-priority` returns `bool`. It does not need to know project-management policy to prove that every object in the list supports `render`.

Types do not prove everything. They cannot decide whether the threshold should be 8, whether five estimated units are accurate, or whether a task title is helpful. Domain checks, tests, and review remain necessary.

Good static guarantees remove mechanical uncertainty so human attention can remain on those domain decisions. A type system becomes ceremony when it asks the programmer to restate facts the compiler already knows without gaining a meaningful boundary. It becomes useful when it makes an invalid program unrepresentable or forces an unresolved alternative into view.

## Project: strengthen the task-list program with types

We will extend Chapter 9's task-list model with:

- optional fixed-width estimates;
- explicit fixed-width priorities;
- checked and throwing coercion examples;
- refinement of present estimates;
- a function-typed priority filter;
- an interface that exposes precisely the behavior the collection needs.

Create `typed-task-list.trn`:

```terrane
namespace typed-task-list

from /core/collections import list

interface task-view
  function render string;
  function estimate-units int8|none;
  function priority-value int8;

trait categorized
  category string = 'general'

  function render-category string;
    return ' ('.concat; this.category, ')'

class task implements task-view uses categorized
  title string = ''
  completed bool = false
  estimate int8|none = none
  priority int8 = 0

  function construct; title string, category string = 'general', estimate int8|none = none, priority int8 = 0
    this.title = title
    this.category = category
    this.estimate = estimate
    this.priority = priority

  function mark-complete;
    this.completed = true

  function render string;
    if this.completed
      return '[done] '.concat; this.title, (this.render-category;)
    return '[ ] '.concat; this.title, (this.render-category;)

  function estimate-units int8|none;
    return this.estimate

  function priority-value int8;
    return this.priority

class urgent-task extends task
  function render string;
    return '[urgent] '.concat; this.title, (this.render-category;)

function high-priority bool; priority int8
  return priority >= 8

class task-list
  private items list of task-view = list

  function add; item task-view
    this.items = this.items.append; item

  function show-estimates;
    for item in this.items
      estimate int8|none = item.estimate-units;
      if estimate != none
        print; 'Estimate: ', estimate

  function show-matching; predicate function from int8 to bool
    for item in this.items
      priority int8 = item.priority-value;
      if predicate; priority
        print; (item.render;)

function main;
  input-priority int = 9
  urgent-priority int8 = input-priority.coerce; int8
  unchecked-priority int = 300
  checked-priority int8|none = unchecked-priority.coerce.checked; int8
  if checked-priority == none
    print; 'Priority rejected: ', unchecked-priority

  chapter task = instance task; 'Draft chapter', 'writing', 5, 4
  chapter.mark-complete;
  review urgent-task = instance urgent-task; 'Review examples', 'book', none, urgent-priority

  tasks task-list = instance task-list;
  tasks.add; chapter
  tasks.add; review

  tasks.show-estimates;
  print; 'High priority:'
  tasks.show-matching; high-priority
```

Run it:

```console
terrane run typed-task-list.trn
```

It prints:

```text
Priority rejected: 300
Estimate: 5
High priority:
[urgent] Review examples (book)
```

Trace the type decisions.

`input-priority` is explicitly `int` because it represents an unconstrained incoming quantity. `coerce; int8` establishes the storage boundary for a valid value. The checked conversion of 300 returns `none` rather than allowing a wrapped or clamped priority.

The class stores `estimate int8|none`. The ordinary task supplies 5, which contextual typing admits as `int8`; the urgent task supplies `none`. `show-estimates` checks a named optional binding before displaying it, so only the known estimate appears.

`task-view` now promises three operations. Consequently, `list of task-view` can render every element, obtain an optional estimate, and retrieve a fixed-width priority without knowing whether the value is a `task` or `urgent-task`.

Finally, `show-matching` accepts `function from int8 to bool`. Passing `high-priority` separates the iteration mechanism from the filtering decision. Another predicate with the same callable contract could select low-priority work without changing the collection class.

The program remains selective about annotations. Loop bindings and obvious call results use inference where no boundary is obscured. Fields, interface methods, function contracts, optional values, fixed-width domain choices, and the callback receive explicit types because those choices matter.

## Terrane style: state contracts, not compiler trivia

A useful annotation answers a question a maintainer might otherwise answer incorrectly:

- Can this value be absent?
- Which concrete numeric range is promised?
- May this collection contain different implementations?
- What behavior must a callback provide?
- What may cross this public boundary?

An annotation that merely repeats the immediately visible constructor may still aid scanning, but it should not become compulsory ritual:

```terrane
review urgent-task = instance urgent-task; # explicit, useful near mixed object code
review = instance urgent-task;             # equally typed when context needs no emphasis
```

Do not select a fixed integer width because generated Rust happens to use one today. Choose it because the Terrane contract needs that range or representation. Do not add a union because several temporary implementation values are convenient to store together. Name alternatives that the domain genuinely permits.

The compiler's representation may specialize, erase, or rearrange type machinery beneath the source. The source types should continue describing observable program promises rather than guesses about backend layout.

## What we learned

Terrane values are always typed, whether a binding spells the type or receives it through inference. Annotations are most valuable at boundaries, empty constructions, optional states, fixed representation decisions, and places where inference would communicate too little intent.

Union types state real alternatives. `T|none` represents optional presence without inventing a sentinel, and direct checks refine named bindings so present values can be used safely. Assignment invalidates a stale refinement.

Coercion selects a declared conversion policy; it is not universal casting permission. The default may throw, while `coerce.checked` yields absence. Different policies such as wrapping, saturation, rounding, and exact arrival remain distinct because they produce different values and failures.

Generic type constructors such as `list of T` and `map of K, V` preserve element contracts without universal boxing. Version one provides these concrete constructors but does not permit source-declared type parameters. Function types describe callable inputs, results, and compatible failure boundaries.

The strengthened task-list program combines inference and explicit contracts rather than choosing one exclusively. Its types expose optional estimates, bounded priorities, interface behavior, and caller-supplied predicates while leaving obvious local mechanics concise.

In Chapter 11, we will distinguish independent values from intentionally shared identity. Assignment, `ref`, `shared ref`, movement, and lifetimes will make explicit when two parts of a program should—or must not—observe the same changing object.
